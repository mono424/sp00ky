## Options Detail

#### `database.endpoint`

The WebSocket URL for your **SurrealDB** instance (e.g., `ws://localhost:8666/rpc` when running locally with the Sp00ky CLI's bundled dev stack). The Sp00ky client connects directly to the database. Optional, and when omitted the client connects in offline-only mode and queues mutations until a remote is configured.

#### `database.store`

- `'memory'` (default): Transient in-memory storage (clears on page reload)
- `'indexeddb'`: Persistent local storage in the browser

With `'indexeddb'`, the local store is **bucketed per user**: each account
gets its own IndexedDB database (`sp00ky-<userId>`, with a shared
`sp00ky-anon` bucket for signed-out sessions), and the client switches
buckets automatically on sign-in/sign-out. Cached rows, query state, and the
offline mutation outbox never leak between accounts on a shared device, and
a user's un-pushed offline mutations resume the next time they sign in. See
[Architecture → Per-User Local Buckets](/docs/reference/architecture#per-user-local-buckets).
With `'memory'`, an auth change resets the store instead (same isolation,
no persistence).

`'indexeddb'` on the default SurrealDB engine needs `@surrealdb/wasm` 3.1.0
or later (the version `@spooky-sync/core` installs). The 3.0.x engine opened
the store but failed every write with `An IndexedDB error occured: idb error`,
so each session quietly ran in memory. From 3.1.0 the engine itself ships as
`@surrealdb/wasm-native`; with Vite, exclude it from dependency pre-bundling
next to `@surrealdb/wasm`, or the dev server serves `index.html` where the
`.wasm` file should be:

If a store cannot be opened even after the client drops and recreates it, the
session runs in memory and logs `falling back to in-memory` at error level;
the next load tries IndexedDB again. Under `localEngine: 'sqlite'` or
`'rows'`, `'indexeddb'` selects that engine's OPFS-backed store instead.

#### `database.workers`

Factories that start the local store's web worker, for a bundler that does not bundle a worker
started inside a dependency. That is the Angular CLI; Vite, Rollup and webpack bundle the built-in
workers on their own, so leave this unset there. Each factory starts a module worker whose entry
imports the module the engine expects, and the app's build bundles that entry:

| Key | Engine | Worker entry imports |
|---|---|---|
| `surreal` | default (`localEngine: 'surrealdb'`) | `@surrealdb/wasm/worker` |
| `sqlite` | `localEngine: 'sqlite'` | `@spooky-sync/core/sqlite-worker` |
| `rows` | `localEngine: 'rows'` | `@spooky-sync/core/rows-worker` |

`.wasm` files to copy, is in the [Angular guide](/docs/guide/angular#setup).

#### `localEngine`

Which engine holds the local cache. All three keep the same rows and answer the same queries; they
differ in what runs underneath.

| Value | What it is | Durable store (`database.store: 'indexeddb'`) |
|---|---|---|
| `'surrealdb'` (default) | SurrealDB compiled to WebAssembly | IndexedDB |
| `'sqlite'` | SQLite compiled to WebAssembly, in a worker | OPFS |
| `'rows'` | sp00ky's own row store, in a worker | OPFS |

<Experimental>
  `'rows'` is experimental. It stores each bucket in one append-only file with a flat index, built
  for this client's reads and writes and nothing else: no SQL engine and no WebAssembly to load (its
  worker is about 30 kB, where SQLite's is over 1 MB with its `.wasm`). It answers every query the
  way `'sqlite'` does, with two differences where SQL leaves the order open: rows that tie on an
  `orderBy`, and the children of a `.related()` without one, come back in id order.
</Experimental>

Under `'rows'`, a write to a table that holds a user's unsent work (the outbox, debounced patches,
failed writes, unsent CRDT edits) is flushed to disk before it resolves. Rows that are a copy of
server state are flushed within about 100 ms instead: a power cut in that window costs a refetch,
never a user's work.

`'rows'` keeps its own indexes, in the same file as the rows and written with them. A field that
holds record links gets one as rows arrive, so a `.related()` never waits for a build; a field a
query filters on with `=` gets one the first time, by one read of the table. A field with only a
handful of distinct values (a boolean, a status) is left to a scan, which reads its matches faster.

A worker takes about 10 ms to start. To have the store open before the app has even loaded, start
it from the page itself: paste `ROWS_PREWARM_SNIPPET` (exported by `@spooky-sync/core`) into an
inline script in `<head>`, ahead of the app's bundle, or call `prewarmRows()` as the first thing
the app's entry does. On a first visit it does nothing; after that it starts the worker and opens
the last user's store while the bundle downloads and parses, and the client adopts it when it
connects. A worker it cannot use (a new release, another user, a failed start) is replaced by a
fresh one.

The same script reads ahead: it asks the worker again for the reads the app made in its first
seconds last time (up to 24 of them), and their answers wait in the page. When the client then
makes one of those reads, it has the answer without a trip to the worker. These are answers from
the store itself, read after it was opened, so they are what the client would have got by asking.
Whatever is left of them is dropped the moment the tab writes, and nothing is read ahead with
`sharedTabs`, where other tabs write to the same store.

#### `database.paintCache`

`localEngine: 'rows'` only, default `true` for a durable store. The engine keeps a copy of what
each query rendered in the app's first seconds (up to about 1 MB, in localStorage). On the next
page load a query is born holding those rows: the first value `useQuery` hands a component is the
list it showed last time, not an empty one, and the component renders once where it used to render
twice. The read that follows is the answer, as always, and replaces the rows when the store says
otherwise; until then the query reports itself unanswered, as any query still loading does.

A copy is dropped the moment this tab writes to a table it came from and taken again from the
query's next render, so it holds what the query last showed. Not used with `sharedTabs`. Set
`false` to keep nothing in localStorage.

By default a provider renders nothing until the client is open, so those rows reach a component
when its query registers, a moment after startup. A provider's `eager` option renders the app at
once, and the same rows are then what the very first render shows, before the local database is
open at all. Each framework guide has a section on it: [React](/docs/guide/react#rendering-before-the-client-is-ready),
[Solid](/docs/guide/solid#rendering-before-the-client-is-ready),
[Solid 2](/docs/guide/solid2#rendering-before-the-client-is-ready),
[Angular](/docs/guide/angular#rendering-before-the-client-is-ready),
[Svelte](/docs/guide/svelte#rendering-before-the-client-is-ready).

#### `database.followerReads`

`localEngine: 'rows'` with `sharedTabs` only. `'leader'` (default) or `'direct'`.

With `sharedTabs` one tab holds the store and every other tab (a follower) reads and writes
through a port into that tab's worker. A follower's read then waits behind whatever the leader's
worker is doing, a sync-down in the other tab included. `'direct'` gives each follower a worker of
its own that reads the store's file beside the leader: its reads cross no tab boundary and wait
for nobody. Writes still go to the leader, and a follower sees every write (its own, the leader's,
another follower's) in the read after it.

The price is in what the browser no longer checks. By default the leader's file handle is
exclusive, so a second writer cannot even open the file; shared handles (Chrome 121+,
`readwrite-unsafe`) leave the leader's Web Lock as the only thing between two writers. Each
follower also keeps the store's index in its own memory. Where shared handles are missing (Safari,
Firefox for now), or a follower's reader fails, that follower reads through the leader as before.

`sharedTabs: true` (one durable store for all tabs of the origin) works with `'sqlite'` and `'rows'`.

#### `logLevel`

Controls the verbosity of logging output:

- `'trace'`: Most verbose, includes all internal operations
- `'debug'`: Detailed debugging information
- `'info'`: General lifecycle events (connected, synced)
- `'warn'`: Recoverable errors and warnings
- `'error'`: Critical failures
- `'fatal'`: Fatal errors that stop execution

This is what the console prints. The page also keeps its last 500 lines for the
[DevTools Logs tab](/docs/reference/devtools), which can record below this
level (say, `debug`) for one tab session without printing more to the console.

#### `persistenceClient`

Determines where small metadata values (the auth token, the stream
processor's persisted state) are stored:

- `'localstorage'` (default): Use browser localStorage
- `'surrealdb'`: Store in the local SurrealDB instance (inside the current
  user's local bucket)
- Custom implementation of `PersistenceClient` interface

Note: the boot-time bucket hint (`sp00ky:last_bucket`) is always written to
plain localStorage regardless of this setting, because the client needs it to pick
the right per-user bucket before any bucket is open.

#### `streamDebounceTime`

Minimum gap (ms) between two re-materializations of one query before
they fan out to `useQuery` subscribers. The first change after a quiet
spell is delivered on the next tick; later changes inside the window
fold into one update at its end, so a burst of synced records (e.g. the
initial library sync) repaints affected views once per window instead of
row-by-row. Lower values repaint bursts more often; higher values reduce
re-render thrash on bursty writes. Defaults to `50`.

#### `crdt`

Load the `loro-crdt` engine at startup (as a separate chunk) so the first
[CRDT field](/docs/client/crdt) opens without waiting for it. Off by default:
Loro is then only fetched when a field is first opened, which keeps it out of
apps that never edit one. Defaults to `false`.

#### `crdtDebounceMs`

How long (ms) the first edit to a [CRDT field](/docs/client/crdt) after a
quiet spell waits before the tab sends it, so a burst of keystrokes travels as
one edit-log row through the outbox. Edits apply to the local Loro document at
once. Defaults to `50`.

#### `crdtSendIntervalMs`

The shortest gap (ms) between two edit-log rows of one CRDT field. While
someone keeps typing, their edits go out on this cadence instead of waiting
for a pause, so other editors see the text a few hundred ms behind, not
seconds. Lower values reach other editors sooner and create more rows (the
SSP folds them into the document either way). Defaults to `200`.

#### `channels`

Settings for [peer to peer channels](/docs/client/channels) on `-- @channel` tables:

- `accept`: per table, `({ kind, from, table, id, row, patch }) => boolean`. Decides whether a peer's
  update, create or delete (`kind`) is applied, after the built-in checks (sender listed by an open channel
  whose query the row matches, fields exist and fit their column type). Without a rule every such write
  is applied.
- `iceServers`: STUN/TURN servers for the default WebRTC transport. Defaults to a public STUN server;
  add TURN for networks that block direct connections.
- `transport`: a `ChannelTransportFactory` that replaces WebRTC (an existing room or relay).
- `confirmTimeoutMs`: how long a peer's persistent value, create or delete shows without the server
  confirming it. Defaults to `5000`.
- `share`: send this user's optimistic writes straight to their
  [other devices](/docs/client/channels#your-own-devices). `share.tables` maps a table to `true`
  (every row), a function `(row) => boolean` (only the rows it passes) or `false`. Tables left out
  are not shared, and nothing is shared unless this is set. Needs `relay`.
- `relay`: the address of the [room relay](/docs/reference/relay) the user's devices meet on
  (`'wss://relay.example.com/room'`), or `{ url, direct }`, where `direct: false` stops two browsers
  from also opening a WebRTC link to each other. Each browser keeps one socket to it, shared by its
  tabs.

Dart and Rust have both: `ChannelsConfig(relay: ChannelRelayConfig(url), share:
ChannelShareConfig(tables: {'game': ChannelShareRule.all, 'note': ChannelShareRule.where(test)}))`
in Dart, `ChannelsConfig::default().share("game").share_rows("note", test).relay(url)` in Rust. A
native client always talks through the relay, so `direct` does nothing there.

In Dart (`spooky_core`) the same keys live on `ChannelsConfig` (`accept`, `iceServers`, `transport`,
`confirmTimeoutMs`), plus `rtc`: the peer connection factory, `flutterWebRtc` from `spooky_flutter`.
Without `rtc` or `transport`, channels report `unsupported`. Rust (`spooky-core`) has the same
`ChannelsConfig` in snake case (`accept`, `ice_servers`, `rtc`, `transport`, `confirm_timeout_ms`),
with `rtc` a factory for the app's own WebRTC stack.

#### `liveInlineBodies`

Carry a changed row's body on the client's LIVE notification (`FETCH out`)
instead of fetching it afterwards, which saves one round trip between another
device's write and this screen. A row joining a view is committed from the
notification either way; with this on, nothing else has to be read before it
renders. The cost is wire bytes: each notification carries its own copy of
the row, once per view that holds it. Defaults to `false`.

#### `refSyncIntervalMs`

Base cadence (ms) for the `_00_list_ref` poll that catches cross-session
UPDATEs that the SurrealDB v3 LIVE-permission gap drops. Defaults
to `500`; non-positive values fall back to the default. One cycle reads
every active query's edges in a handful of round trips (batched by a
row budget, views past 1,000 rows only every 15s), backs off toward 5s
while nothing changes, and never runs back-to-back: the next tick waits
at least as long as the previous cycle took. Statements on the remote
connection run concurrently (up to 6 in flight), so the poll does not
hold registrations or one-shot reads behind it.

#### `persistCircuit`

Persist the in-browser stream processor's store as a snapshot in the local
store, so a reload restores it and only steps in what changed since instead
of re-downloading the working set. Defaults to `true` under
`localEngine: 'sqlite'` and `'rows'` (the OPFS-backed stores hold the bytes)
and `false` otherwise. Snapshots are written on `circuitCheckpointMs` (default `30000`)
and when the page goes hidden, never per ingest. Without a snapshot the
circuit is primed by reading the cached rows back out of the local store.

#### `circuitProjection`

Keep only the fields registered queries evaluate (filter predicates, join
keys, sort keys, plus `id`/`_00_rv`) per row inside the in-browser circuit.
Defaults to `true`. Bodies are rendered from the local store, so the circuit
never needs the rest; on rows with large text fields this is the difference
between a few hundred megabytes of wasm heap and a few megabytes.

#### `allowRawRemote`

Opt back in to the raw remote escape hatches (`db.useRemote`, `db.remoteQuery`,
`db.queryRaw`) when the generated schema's `policy.queryAllowlist` is `warn` or
`enforce`. With the [query allowlist](/docs/guide/query-allowlist) on, the SSP
only registers shapes `spky generate` recorded from the query builder, so a
hand-written SurrealQL string can never be allowlisted; these methods throw
(`... is disabled because sync.queryAllowlist is on for this schema`) unless
this flag is `true`. Defaults to `false`. The gate is client-side only: direct
SurrealDB reads under table `PERMISSIONS` are unchanged.

## Diagnostics

The client exposes a small number of read-only getters intended for
e2e regression guards and runtime instrumentation.

#### `pendingMutationCount` and `subscribeToPendingMutations`

Live count of mutations queued for upstream sync. The subscribe
variant fires on enqueue/dequeue so a UI can render a "saving…"
indicator without polling.

#### `liveRetryCount`

Number of times the initial `_00_list_ref[_user_*]` `LIVE SELECT`
subscription had to retry on the most recent `setCurrentUserId`
call. Stays at `0` when the SSP's pre-emptive per-user table
creation got there first (the default path); a value above `0`
means the LIVE registration hit a "table not found" race and the
client fell through to the poll fallback while retrying. The e2e
suite's `z-auth-bootstrap.spec.ts` asserts this stays `0` after a
clean signup so the pre-emptive path can't silently regress.
