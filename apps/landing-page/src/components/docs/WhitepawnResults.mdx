response time. Polls run every 10 ms plus database request time.

**Write rate and catch-up**

Full cases write 3,000 rows at a target of 50 rows/s for 60 seconds, then import
30,000 rows at a target of 1,000 rows/s for 30 seconds. Imports use 100-row
transactions with at most four in flight. Smoke runs each phase for two seconds,
committing 100 and 2,000 rows respectively. All completed cases had zero failed
load-phase rows.

Throughput counts **committed source rows per write interval**. It does not
establish the rate at which the SSP publishes them. After writes finish, the
driver reads expected source windows, then times residual publication catch-up.
The pipeline can drain while those source queries run, so the two durations
below must be read together; residual catch-up alone is not total propagation
delay.

**Graph sharing and memory attribution**

With view sharing enabled, adding the identical subscriber kept graph count at
**17** and increased merged followers from **0 to 1** in every case. A follower
shares another registration's computation; the graph owner is excluded from the
follower count. After import, the smoke cases retained sharing, while both 100K

**Resource-limited tiers**

In these reports, neither 1M case nor the 10M case ran. The standard run excluded
1M compact on projected host memory and 1M PGN on projected disk, host memory
and Docker memory. The large run excluded all three larger cases on those
three checks. Both commands exited nonzero, retaining their completed 100K
results.

consumption or minimum hardware requirements. They scale the completed compact
case by populated rows, including the 33,000 load inserts, with a 1.25× margin.
PGN projections also include payload allowances.
