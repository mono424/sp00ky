Buckets provide a type-safe file storage abstraction for uploading, downloading, and managing files in your Sp00ky application. They integrate directly with your SurrealDB schema for permission control and with the Sp00ky CLI for guided setup.

## Defining a Bucket

Buckets are defined in SurrealQL using the `DEFINE BUCKET` statement. Create a `.surql` file in your `src/buckets/` directory:

  code={code10}
  lang="sql"
/>

### Permission Variables

- **`$action`**: the operation: `'put'`, `'get'`, `'head'`, `'delete'`, `'copy'`, `'rename'`, `'exists'` or `'list'`
- **`file::key($file)`**: the file path/key being acted on
- **`$target`**: the destination key, on `'copy'` and `'rename'` only

This example allows unrestricted reads and deletes, and restricts uploads to the
four image extensions. `list` is denied to record and guest sessions by the
engine itself, whatever the clause says.

### Size limits are a client-side rule

`COMMENT 'sp00ky:maxSize=<bytes>'` is read by `spky` into the bucket's generated
config, and `useFileUpload` rejects an oversized file before it leaves the
browser.

<Note>
Do not express a size limit as a permission predicate. SurrealDB evaluates a
bucket's PERMISSIONS clause BEFORE the upload exists, so `file::head($file).size`
there is the size of whatever is already stored at that key, not the size of what
is being uploaded. A `file::head($file).size <= N` gate therefore lets every
first upload through at any size, and denies legitimate overwrites of any file
that is already over the limit. Older schemas carry that predicate because
SurrealDB 3.0.x did not enforce per-file bucket actions at all; 3.1.x does.
</Note>

## Local Caching

Bucket reads go through a durable client-side cache. Bytes land in OPFS under `sp00ky-blobs/<bucketId>/<bucket>/<path>`, so a file downloaded once survives a reload, paints instantly on the next visit, and is available offline. The cache is namespaced per signed-in user and is on by default wherever OPFS is writable; elsewhere it degrades to per-tab memory.

Nothing expires on a timer. A file is dropped only when the app invalidates its path (`put()` and `delete()` do this for you), when boot reconcile finds no file behind a manifest row, or when the cache exceeds its byte budget — in which case the least-recently-used unpinned entries that nothing is currently rendering go first.

<CodeBlock
  code={`const client = new Sp00kyClient({
  // ...
  blobCache: {
    enabled: true,          // default
    maxBytes: 256 * 1024 * 1024,  // default: min(512 MB, quota × 0.25)
    clearOnSignOut: false,  // default — cached files are per-user namespaced
  },
});

const bucket = client.bucket('profile_pictures');

</Note>

## Current Limitations

- **Memory backend only**: Files are stored in memory and not persisted across restarts. Additional storage backends (S3, filesystem, etc.) are planned.
- **No streaming**: Files are uploaded and downloaded as complete blobs. No chunked upload or progress tracking yet.
- **No transactions**: Bucket operations do not participate in database transactions.
