## Restoring from a Backup

<CodeBlock
  code={code6}
  lang="bash"
/>

Here's what happens when you run it:

1. The scheduler queues the restore and the CLI prints the restore ID.
2. Ingestion stops. New writes get a `503`, and proxy queries and SSP registrations are rejected while the restore is running.
3. Both databases are wiped and reloaded from the same backup file. Main SurrealDB and the scheduler's snapshot replica stay in sync.
4. Pending items are cleared. That covers the in-memory event buffer, the write-ahead log, and any per-SSP message buffers.
5. Connected SSPs are evicted. They'll re-register on their next heartbeat against the restored state.
6. Sp00ky Cloud gives the restored database's access methods new signing keys and checks that no forged token gets in (see [Signing keys after a restore](#signing-keys-after-a-restore)). Only then is the restore reported as done.
7. The CLI polls for progress every 5 seconds (up to 5 minutes) and shows the current phase as it moves from `queued` to `running` to `completed`.
8. Once the restore finishes, your migrations run again against the restored database.

<Warning>
Restoring replaces your current data with the backup. Anything you wrote after the backup was taken is gone. If you're not sure, take a fresh backup first.
</Warning>

### Pay-as-you-go projects

A pay-as-you-go project has no scheduler, so Sp00ky Cloud takes and restores its backups itself, with the same commands and the same backup files. A restore wipes the database, imports the backup and reloads the sync engine, which picks up the restored data on its own; run your migrations again afterwards as above.

To change SurrealDB version, use [`spky db upgrade`](/docs/cloud/database-upgrades), not a backup and restore: it keeps everyone signed in, and takes a backup of its own first.

### Signing keys after a restore

Every restore, on VMs and on pay as you go, gives each record `DEFINE ACCESS` a new signing key, so everyone signed in has to sign in again. SurrealDB's export does not contain the keys (it writes `'[REDACTED]'`), and a database restored with that placeholder would let anyone sign a valid token for any user. Sp00ky Cloud checks the restored database after every restore, whatever scheduler version imported it, and refuses to report a restore as done until no access accepts such a token.

Two kinds of access cannot get their key back. Admin impersonation (`_00_impersonate`) works again after your next `spky deploy`, which sets its key. An access that verifies tokens of an outside issuer with a shared key is removed by the restore: run its `DEFINE ACCESS` statement again afterwards (the restore's metadata names it).

<Note>
If the main database gets wiped but the snapshot replica fails to import, the scheduler stays in the `restoring` state on purpose. That blocks reads until someone re-runs the restore. Serving traffic from a half-restored cluster would give back wrong data.
</Note>

## From the dashboard

The scheduler's [admin dashboard](/docs/reference/admin-dashboard#backups) has a Backups tab that does everything above except `reset`: create, list, restore, delete, configure the schedule and retention, and turn [point-in-time recovery](#point-in-time-recovery) on and restore to a moment. It shows the same catalog as `spky backup list`, joined to what the scheduler itself knows about each backup, and a restore there reports the real stages as the scheduler moves through them (`queued`, `running`, main database restored, replica restored, done). It goes through Sp00ky Cloud like `spky backup restore`, so the signing keys are renewed the same way, and migrations still have to be run again afterwards.

<Note>
**How the dashboard talks to Sp00ky Cloud.** The control plane injects `SPKY_CLOUD_API_URL` and `SPKY_CLOUD_PROJECT` into the scheduler container (only the scheduler, never the SSPs). The scheduler then calls an allow-listed route family, `/v1/internal/projects/{slug}/…` (restart, deployment status, and the backup routes minus `reset`), authenticated with the project's existing `SPKY_AUTH_SECRET`. No new credential is created. A control plane that supports this lists `scheduler_link` under `features` in its `/health` response; a scheduler without the link still works and marks those actions as unavailable.
</Note>

If a backup started from the dashboard fails with **Sp00ky Cloud rejected this
scheduler's credentials**, that is the control plane refusing the scheduler's
`SPKY_AUTH_SECRET`, not your login expiring. The dashboard reports it as a
`502` carrying the code `cloud_auth` and keeps you signed in, precisely so the
real cause is visible; an earlier version relayed the upstream `401` and
signed the operator out instead, which hid it. Check that the project still
has a stored auth secret and that the scheduler container was recreated since
the secret last changed, then retry. The catalog degrades the same way rather
than disappearing: the Backups tab still loads and shows the message where the
list would be.

/>

| Option | What it does |
| :--- | :--- |
| `--enabled` | Turn automatic backups on or off (`true`/`false`) |
| `--schedule` | Cron expression in UTC for how often to back up (e.g. `"0 2 * * *"` for daily at 2 AM) |
| `--retention` | Keep the newest N backups, whatever their age. `0` sets no count |
| `--keep-hourly`, `--keep-daily`, `--keep-weekly`, `--keep-monthly`, `--keep-quarterly`, `--keep-yearly` | Keep the newest backup of each of the last N hours, days, weeks, months, quarters or years |
| `--recommended` | `--keep-daily 3 --keep-weekly 5 --keep-quarterly 4` with no count limit. Any `--keep-*` or `--retention` you pass alongside wins |

### How retention decides

Every option is a rule for what to **keep**; a completed backup that no rule keeps is deleted, from storage and from the list. With nothing set, every backup is kept.

The tiers run in order: newest N, then hourly, daily, weekly, monthly, quarterly, yearly. Each keeps the newest backup of each of its last N periods, and skips any period an earlier tier already holds a backup of. That is what makes them add up: with `--recommended` on a daily schedule you keep

- the last **3 days**,
- one backup for each of the **5 weeks** before those, which always reaches at least 31 days back,
- the last backup of each of the **4 quarters** before that, so about a year,

twelve backups in all. Five weeks rather than four because weeks are calendar weeks (Monday to Sunday, UTC): four only reach 24 to 29 days back, depending on the weekday.

A period only counts when it has a backup, so a night that failed widens the window instead of leaving you with fewer backups. The newest backup is always kept.

**Named backups are never deleted by retention.** `spky backup create --name before-migration`, and the backup `spky backup reset` offers to take, stay until you delete them yourself.

A pay-as-you-go project is backed up every day at 03:00 UTC with the recommended tiers, until you configure retention yourself. Scheduled backups pause while a project is stopped at its [spend cap](/docs/cloud/billing#spend-cap).

## Point-in-time recovery

A daily backup can lose a day of work. With point-in-time recovery on, Sp00ky Cloud also records every change to the database, and a restore can reach **any moment of the last 48 hours**, not just the moment a backup was taken.

<CodeBlock
  code={codePitr}
  lang="bash"
/>

`--at` takes RFC 3339 (`2026-11-15T13:45:00Z`), a date and time in UTC (`2026-11-15 13:45`), or a span back from now (`90m ago`, `2h ago`, `1d ago`). The dashboard's Backups tab has the same restore, with a picker in your own time zone.

### How it works

The database keeps a change feed (`CHANGEFEED 1d` on the database), and Sp00ky Cloud reads it **every 15 minutes** into a file next to your backups. These are not backups of their own: each holds the rows the transactions of those 15 minutes wrote, exactly as they were written.

A restore to a moment loads the newest full backup that finished before it, then replays the recorded transactions from that backup's start up to the moment, one transaction at a time and in order, so the result is the database exactly as it was then. Tables made after the backup come back with their definitions and permissions.

Some things follow from that:

- **The newest moment you can reach is the last reading**, at most about 17 minutes ago. If the database itself is lost, the changes since the last reading are lost with it.
- **It needs full backups to replay from.** Turning it on starts one about ten minutes later (a backup has to begin after the recording does to be replayed from), so the first moments become reachable once that backup has finished. While it is on, Sp00ky Cloud starts one whenever the newest is more than a day old, schedule or not. Every backup a restore within the 48 hours may start from is kept whatever your retention says.
- **A restore, a database upgrade or a project move starts a new recording.** The moments before it stay reachable until they leave the window, but no restore replays across it. A backup is started to reopen the window.
- **A restore takes no last reading first.** Undoing a restore you regret reaches the last reading before it, up to about 17 minutes earlier.
- **Writes cost a little more.** Every transaction also writes its change into the feed, and the database keeps a day of it on disk.
- **Schema changes land at 15-minute resolution.** The feed carries rows, not `DEFINE` statements, so each reading also records the definitions (fields, indexes, events) of every table that changed, and a restore applies them at the reading's start. Database-wide definitions (functions, params, accesses) are not recorded; your migrations and `spky deploy` set those, and migrations run again after a restore anyway.
- **It does not work with `sync.transport: changefeed`** yet, which reads the whole database's feed for its own ingest. Turning it on there reports the problem instead.

`spky backup configure` prints the window a restore can reach. Turning point-in-time recovery off takes the feed off the database and deletes the recordings.
