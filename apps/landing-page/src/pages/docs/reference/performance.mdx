The WhitePawn benchmark measures database writes reaching live, 50-row windows
through SurrealDB's real changefeed. The completed 100K-game runs published new
scroll windows in **165–377 ms p50** and isolated mutations in **63–145 ms p50**.
The tables below preserve each run separately, including resource limits and
backlog observations. These measurements use the canary.301 engine and precede
the newer index and batching changes described [below](#big-tables-give-each-list-its-index).

The [repository benchmark](https://github.com/mono424/sp00ky/tree/main/apps/benchmark)
also includes direct-ingest microbenchmarks. Their results appear
[later on this page](#direct-ingest-microbenchmarks), with a different measurement
boundary.

## WhitePawn benchmark

Measured on **October 11, 2026**: Apple M3 Max, 14 cores, 36 GiB RAM, macOS arm64,
Node 22.22.3, Docker 29.4.0 with 15.66 GiB available to Docker, and SurrealDB
**3.1.5**. Each case used a fresh, disk-backed database, one release scheduler and
one release SSP from package version `0.0.1-canary.301`. Other development
containers were running on the host, so these
are local observations on a shared machine.

The synthetic fixture has twenty game collections and 256 players; 80% of games
belong to one collection. Windows project game metadata and both players' names,
ordered by `sort_index, id`, with tied sort keys. PGN text is stored in the heavy
fixture but excluded from the projected window. A 100-step scroll trace keeps at
most twenty registrations and exercises eviction, revisits, collection filters
and a second subscriber to an identical query.

## Big tables: give each list its index

A view starts from the rows its filter could match. Without help that is
every row of the table, so on a table of a million rows each new list
window costs the SSP a pass over all of them, even for `LIMIT 50`.

The SSP holds the same indexes SurrealDB does. Every plain
`DEFINE INDEX … FIELDS` on a synced table is mirrored: one applied by
`spky migrate` or a deploy arrives with the next schema poll, and one
defined by hand in the SurrealDB console within about a minute. A
`REMOVE INDEX` is followed the same way.

A windowed list reads its window straight off an index when:

- its `WHERE` is equalities (`field = value` or `field = $param`, joined
  with `AND`) on the index's leading fields, in any order, and
- its `ORDER BY` is the rest of the index, in order, each field `ASC` or
  `DESC` as you like. A trailing `id ASC` tiebreaker is free.

<CodeBlock code={indexedListCode} lang="sql" />

Once its index is built, registering such a window touches the rows it
returns, and a write re-reads only that window. Any other filter with equalities
on an index's leading fields still starts from that index range instead
of the whole table, an `OR` with such equalities in every branch reads
one range per branch, and `WHERE id = $id` reads that one record.
Full-text, vector (`HNSW`, `MTREE`) and `COUNT` indexes are not used, and
range conditions (`<`, `>`) narrow nothing on their own.

Results are identical either way; an index changes only the cost. On a
1M-row table with 422k rows in one list, 20 scroll windows took 14.6 s
to register without the index and 0.6 s with it (the first window builds
the index, each one after that takes ~30 µs). The index costs about
100 bytes per row of the table and is built when a view first needs it.
It stays for an hour after its last view goes, so the next list opened
does not pay the build again, and a restarted SSP rebuilds the indexes in
use before it takes traffic.

Restored active views now prewarm the indexes their plans select before the
SSP reports Ready. Schema changes prewarm replacement indexes before evaluating
replacement graphs, including a changed definition under the same index name.
Live registration prewarms under a circuit reader and rechecks the registration
identity and merge owner under the writer before installing a graph. A first-ever
index still costs a pass over its table and blocks ingest writers while building;
prewarming shifts this cost out of snapshot evaluation, rather than removing it.
Registration metrics report this work separately as `index_build_ms`,
`indexes_built` and `rows_indexed`.

Rust embedders can call `Circuit::prewarm_query_indexes(&plan, params)` for a
selected plan, `Circuit::prewarm_active_indexes()` for registered graphs, or
`Collection::prewarm_index(&definition)` for one index. Each returns
`IndexBuildStats` (`indexes_built`, `rows_indexed`, `index_build_ms`); already built
indexes return zero work. `Circuit::set_table_meta_timed` applies schema changes
and returns the same statistics. Timed registration exposes index build fields
in `RegTimings`, and `Circuit::step_timed` separates store application from DAG
stepping with `StepTimings`.

Permission semijoins and antijoins retain keyed witness counts and reverse left
lookups. Ingest reevaluates affected join keys, including changes to a row body
whose membership stays the same. Duplicate witnesses and unrelated changes do
not rescan the left table. Distinct updates only changed keys. These indexes add
memory proportional to retained input keys; changing a witness shared by many
left rows still costs work proportional to that affected set.

### Batches and measurements

The scheduler drains already queued ordinary changes into batches of up to 128
records and 1 MiB, with no wait to fill a batch. An SSP advertises support at
registration; older SSPs and replay continue receiving individual `/ingest`
requests. Each batch applies source changes in order and steps affected graphs
once. Jobs, users and internal lifecycle records use their existing single-row
paths. Publication waits for every surviving source row, with the existing
five-second visibility fallback and 16-probe concurrency limit.

Live view details include separate registration and ingest stage timings. The
same circuit-step measurement is shared by every view affected by that request;
it is not exclusive CPU time for each view. A batch contributes one materialization
sample and one update-count increment to each affected view. Publication wait and
database transaction time remain separate queue and OpenTelemetry measurements.

Successful registration and ingest requests taking at least 250 ms attempt to
retain sanitized evidence in the
private `_00_sync_evidence:slow_operations` ring. Evidence writes are best effort,
with at most four in flight per process and no waiting queue. Requests beyond
that budget increment `ssp_slow_evidence_dropped_total`. Its newest 100 samples survive view TTL
cleanup and service restarts, and are available through the scheduler's
`GET /admin/api/views/history` or MCP `view_history`. Samples include masked query
shapes and stage timings, without SQL text, bindings, user or session identifiers.
Use this history together with publication incidents when investigating a stall.

<Note>
**Define the index your list query needs.** For every list over a big
table, the equality fields of its `WHERE` followed by its `ORDER BY`
fields make the index. It is the same index SurrealDB wants for the
same query, so the database's own reads get faster too.
</Note>

<Note>
**Keep results bounded.** Smaller result sets reduce the data a live query
must materialize and a client must consume. Measure the actual query shape and
source table size when sizing a deployment.

- Always include `LIMIT`.
- Paginate on scroll. Revisiting a retained active window can avoid a new
  registration; an evicted window needs registration again.
- Scope by the viewer: `WHERE author = $auth.id`, `WHERE thread =
  $current_thread_id`.

The scheduler load-balances views across SSPs. Each SSP still holds its
synced source tables, so adding SSPs spreads view computation but also
replicates source memory and ingest work. Measure both before scaling out.

The small-view fixture below measures up to 2,000 views on one SSP. That result
does not establish capacity for other query shapes or multi-SSP deployments.
</Note>

FROM comment` canary, then asserts the canary's cache size equals
the seeded count, sampled cache entries are real comment IDs from
the seeded range, and inserting a new comment grows the cache by
exactly one with that exact ID present.

### Reproduce

```bash
# Prerequisites: Docker + cargo build --release -p scheduler -p ssp-server
pnpm -F @spooky-sync/benchmark build

# Full sweep across both axes plus the secondary suites, 3 runs each.
node apps/benchmark/dist/run-3x.js

# Single point on the realistic-row axis:
node apps/benchmark/dist/index.js subquery-depth \\
  --rows 30000 --row-bytes 900 --ingest-events 30

# Single point on the fat-row axis:
node apps/benchmark/dist/index.js subquery-depth \\
  --rows 1000 --row-bytes 2000000 --ingest-events 30

# Verify the SSP is genuinely running on the seeded data:
node apps/benchmark/dist/verify-bootstrap.js --rows 1000 --row-bytes 2000000
```

`results/<suite>/`. The 3-run aggregate lives at `results/aggregated.md`.
