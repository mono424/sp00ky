Two users. Same thread. Both typing at the same time.

With a normal database, somebody's changes get silently overwritten. Locking makes the UX terrible. Server-side merging is a nightmare for character-level edits.

**CRDTs fix this.** A Conflict-free Replicated Data Type guarantees that any two replicas merge automatically, no matter what order edits arrive in. Every peer converges on the same result.

Sp00ky uses [Loro](https://loro.dev) under the hood. You annotate a field, and you get real-time collaborative editing with cursor presence. Each client sends only its own edits, through the same outbox and sync pipeline as every other write. The server folds those edits into the canonical document and writes the field back as plain text, so lists, search and filters keep working on it.

## 1. Annotate your schema

Put `-- @crdt <kind>` above a `TYPE string` field, and `-- @cursor` if you want remote cursors:

<CodeBlock code={schemaCode} lang="sql" fileName="schema/src/schema.surql" />

| Annotation | What you get |
|---|---|
| `@crdt prosemirror` | A [loro-prosemirror](https://www.npmjs.com/package/loro-prosemirror) tree. For rich text in ProseMirror-based editors (TipTap, Milkdown, ...). |
| `@crdt text` | One `LoroText` named after the field. For plain-text inputs. `@crdt` alone means `text`. |
| `@cursor` | Per-session presence for the field, so editors can show each other's cursors. |

The rules, all checked by `spky generate`:

- The field must be `TYPE string` (or `option<string>`) with no `VALUE` or `ASSERT` clause. The server owns its value.
- Top-level fields only, and not on `TYPE RELATION` tables.
- The `surrealism` deploy mode is refused: the fold runs in the SSP, and that mode has none.
- The names `<table>__crdt_log`, `<table>__crdt_presence`, `_00_crdt_doc` and fields ending in `__crdt` are reserved.

Then run `spky generate` and apply the schema (`spky migrate` / `spky deploy`). Who may read a document's edits, and who may write them, is exactly who may read and update the record: the generated tables reuse the parent table's `select` and `update` permissions.

## 2. The field is plain text

The annotated column no longer holds anything a client writes. It is the document's plain text, written by the server each time it folds the edit log. Read it like any other column: render it in a list, search it, filter or order on it.

<CodeBlock code={previewCode} lang="tsx" />

- **Write it only when creating the record.** A `db.create` may set the initial text, so a new record shows it before the first fold (put the same text in the field's draft document). After that a client write keeps the old value; leave the field out of `db.update`.
- **It trails live edits.** The column changes when the server folds, typically a few seconds after the last edit (at most one fold per field every 10 s by default) (see [the fold](#the-server-fold)). Inside an open editor you read the live document instead.
- **`prosemirror` renders as lines.** Block nodes (paragraphs, headings, list items) become lines, hard breaks become newlines, and formatting is dropped.
- **Keep it out of the sync engine with `@opaque`.** Add `-- @opaque` next to `@crdt` when the text is large or sensitive and you never filter on it; see [`@opaque`](/docs/schema#syncing-a-field-without-indexing-it-opaque).

Each fold also writes `<field>__crdt` on the record, a stamp of the folded version (its `rev` and the Loro version it covers). You don't need to read it.

<Warning title="No migration from text or from older canaries">
  Annotating a field that already holds text does not import that text: the document starts empty, and the first fold after someone edits replaces the column with the document's text. CRDT state written by earlier canaries (inline snapshots on the record) is not read either.
</Warning>

`closeCrdtField` resolves once the edits not sent yet are handed to the outbox, so awaiting it before navigating away loses nothing. Offline it resolves at once and the edits stay on the device until the field is next opened online; on a connection that has not noticed it is down it waits at most 4 seconds.

## How it syncs

Nothing about a CRDT field bypasses the sync pipeline. For a table with `@crdt` fields, `spky generate` adds:

| Table | Holds | Written by |
|---|---|---|
| `<table>__crdt_log` | Append-only edit log: one row per batch of one client's edits (`doc`, `field`, `author`, `peer`, `data`, `size`, `created_at`). | Clients create rows (where the parent's `update` rule allows), the SSP deletes them once folded. No updates. |
| `<table>__crdt_presence` | One presence row per session and field (`@cursor` only). | Each session its own row. |
| `_00_crdt_doc` | The canonical snapshot of each (record, field), with its `rev`. | The SSP only. Never synced: a device reads it on demand, when it opens a field it holds nothing for, or when log rows depend on edits already folded away. |
| `_00_crdt_peer` | Which user owns which Loro peer id. | Clients claim ids, nobody changes or deletes them. |

**Up.** Typing changes the tab's local Loro document right away. After a pause of 300 ms (`crdtDebounceMs`, and at most 2 s into a burst), the tab exports only its own new operations as one Loro update and creates one `<table>__crdt_log` row through the ordinary outbox, so edits survive offline, reloads and retries like any other write. Each tab edits under a random Loro peer id that it claims for the signed-in user in `_00_crdt_peer`; the database refuses a log row whose peer the writer does not own.

**Down.** An open field is an ordinary query on its log rows, so other clients' edits arrive through the normal sync pipeline on the same SurrealDB connection, with no extra LIVE query, and are merged into the open document.

**The acceptance rule.** Before any client or the server imports a log row, it checks that the blob is a Loro update (not a snapshot), at most 256 KiB, and that every operation in it was made by the row's `peer`. A row that fails never enters any document, anywhere, so a client cannot inject edits under someone else's name or replace history with a crafted snapshot.

**Locally.** The device keeps its merged document and how far each of its peers' edits got into the outbox in `_00_crdt_local`. Edits made offline, or just before a reload, are sent later under the peer they were made with. Signing out does not send them under the next user: they wait in the old account's local store.

### The server fold

The SSP is the only writer of the canonical document. To keep its CPU flat it folds rarely: a field is folded once its log has been idle for a while, or once enough rows or bytes are pending, and never more often than a minimum gap. A fold takes a lease on the field's `_00_crdt_doc` row, imports the accepted log rows into the snapshot, writes the new snapshot and the record's plain-text column in one transaction, and then deletes the rows it folded. Several SSPs in a cluster are safe: the lease and a compare-and-swap on `rev` mean exactly one of them publishes each version.

Nothing waits on a fold. A late fold only delays the plain-text column and the snapshot new devices start from; live editors exchange edits through the log directly.

The thresholds are SSP environment variables:

| Variable | Default | Effect |
|---|---|---|
| `SPKY_CRDT_FOLD_IDLE_SECS` | `5` | Fold a field once its log has had no new rows for this long. |
| `SPKY_CRDT_FOLD_MAX_ROWS` | `200` | ...or once this many rows are pending, however active it is. |
| `SPKY_CRDT_FOLD_MAX_BYTES` | `262144` | ...or once this many bytes are pending. |
| `SPKY_CRDT_FOLD_MIN_GAP_SECS` | `10` | Never fold one field more often than this. |
| `SPKY_CRDT_FOLD_WORKERS` | `2` | Folds running at once on one SSP. |
| `SPKY_CRDT_FOLD_TICK_MS` | `5000` | How often the SSP looks for fields due a fold. |
| `SPKY_CRDT_PRESENCE_TTL_SECS` | `60` | Presence rows older than this are swept. |
| `SPKY_CRDT_CACHE_SIZE` | `1024` | Hot documents kept in memory between folds. |

Self-hosted, set them on the SSP process ([Self-hosting](/docs/self-hosting)). On Sp00ky Cloud, set them for the `ssp` role in [`deployment.env`](/docs/cloud/deploying#infrastructure-environment-variables). The SSP's `/info` reports fold counters under `crdt` ([SSP API](/docs/reference/ssp-api#get-info)).

## Limitations

- **Two kinds.** `text` and `prosemirror`. The plain-text column renders those shapes only.
- **The column trails the editor.** List previews update when the server folds, also for your own edits.
- **Every fold rewrites the record.** The column and its `__crdt` stamp are an update of the parent row, so `VALUE time::now()` fields such as `updated_at` move on each fold, and the row syncs to everyone watching it.
- **Impersonation is read-only here.** An [impersonation](/docs/client/impersonation) session cannot write edits or presence.
- **JavaScript clients only.** The Dart client (`spooky_core`, Flutter) throws `UnimplementedError` for CRDT fields.
- **API may change** while experimental.

export function CollaborativeEditor(props: { field: CrdtField }) {
  let ref: HTMLDivElement | undefined;
  let editor: Editor | undefined;

  onMount(() => {
    const doc = props.field.getDoc();

    editor = new Editor({
      element: ref,
      extensions: [
        StarterKit.configure({ history: false }), // Loro handles undo
        Extension.create({
          name: 'loroSync',
          addProseMirrorPlugins: () => [
            LoroSyncPlugin({ doc }),
            LoroUndoPlugin({ doc }),
            keymap({ 'Mod-z': undo, 'Mod-y': redo, 'Mod-Shift-z': redo }),
          ],
        }),
      ],
    });
  });

  onCleanup(() => editor?.destroy());
  return <div ref={ref} />;
}`;
