`spooky-core` (lib `spooky_core`) is the native Rust client for sp00ky. It runs the same engine as
the TypeScript (`@spooky-sync/core`) and Dart (`spooky_core`) clients, so a Rust desktop app, a
Flutter app and a web tab sync the same rows the same way:

- **Local-first.** Rows live in a sqlite store, one file per signed-in account. Queries paint from it
  before the network answers. Writes apply at once and sync through an outbox that survives restarts.
- **Live.** A query is a materialized view. The in-process circuit (the `ssp` crate, no FFI) keeps it
  current as local writes land, and the server's membership keeps it in step with every other client.
- **Any executor.** The engine runs on its own thread with its own tokio runtime. `Sp00kyClient` is
  `Send + Sync + Clone`, and its futures and watch channels work from GPUI, smol, tokio or a plain
  `block_on`.

<Note>
  The crate is not on crates.io yet. Install it from git, and pin a `rev` for reproducible builds.
  It needs Rust 1.85 or newer.
</Note>

The generated `db.rs` holds:

| Item | What it is |
| --- | --- |
| `schema()`, `SURQL_SCHEMA` | The runtime schema and the SurrealQL for the local store, server-only (`-- @nosync`) fields stripped. |
| `config(DatabaseConfig)` | A `Sp00kyConfig` for this schema. Start every client from it. |
| `Note`, `NotePatch` | A serde struct per table (`id` plus every synced field) and an all-`Option` partial update. |
| `Note::rank`, `Note::owner`, ... | Typed field tokens: each only takes operands of its column's type. |
| `AuthApi` | `sign_in_<access>` / `sign_up_<access>` per `DEFINE ACCESS`, params as `&str`. |
| `Backends` | One method per backend route, when you pass OpenAPI specs (see [Backend jobs](#backend-jobs)). |
| `AppDb` | The facade: `AppDb::new(client.clone()).note()`, `.auth()`, `.run()`. |

`record<..>` fields are `String`s holding `table:id`, `datetime` fields are `spooky_core::typed::Datetime`,
`option<..>` fields are `Option`s.

## Open the client

<CodeBlock fileName="src/sync.rs" code={openCode} lang="rust" />

`Sp00kyClient::open` starts the engine thread and runs the local half of boot: the store opens, the
schema is provisioned, the circuit is restored from its snapshot and the cached session is restored.
It returns once a query registered next can paint from the local cache. Connecting, verifying the
session and registering queries with the server run in the background.

Without `.endpoint(..)` the client is local-only: writes and live queries work, nothing syncs. That is
also the quickest way to test your own code (see [Tests](#tests)). For a local `spky dev` stack the
endpoint is `ws://127.0.0.1:8666/rpc`.

The other knobs are public fields on the config:

| Field | Default | What it does |
| --- | --- | --- |
| `database.store` | `StoreType::Memory` | `StoreType::File(path)`: sqlite files derived from `path` (`spooky.db` becomes `spooky.<bucket>.db`, one per account). |
| `database.max_concurrent_queries` | `6` | Remote reads in flight at once. Writes go one at a time in a lane of their own. |
| `database.token` | `None` | A token to authenticate with on connect. |
| `persistence` | `PersistenceConfig::Session` | Where the boot hint and auth token live: a session database next to the store, or `Memory`. |
| `blob_cache` | in memory, 256 MB | `BlobCacheConfig { directory, max_bytes, clear_on_sign_out }` for bucket files. |
| `stream_debounce_ms` | `50` | Minimum gap between two re-materializations of one query. |
| `ref_sync_interval_ms` | `500` | Base cadence of the membership poll. |
| `enable_anonymous_live_queries` | `false` | Realtime sync while signed out. Must match the server's `anonymousLiveQueries`. |
| `sync_health` | degraded after 3 failures | `SyncHealthConfig::DISABLED` never reports degraded. |
| `reconnect` | 15 s backoff cap, 20 s heartbeat | `ReconnectConfig`: backoff, heartbeat interval and timeout, connect timeout. |
| `circuit_checkpoint_ms` | `30000` | How often a changed circuit is snapshotted to the store. |
| `channels` | `None` | Peer to peer channels (see [Channels](#peer-to-peer-channels)). |

## Authentication

<CodeBlock code={authCode} lang="rust" />

`sign_in` and `sign_up` go through `DEFINE ACCESS <access>` with the params it declares. They resolve
after the account switch: that user's local store is open and the registered queries run against it.
`sign_out` pushes queued writes first while the session is still valid.

`auth_state()` (and `auth_watch()`) carries the user id, the user row (`current_user`), the token, the
access method, `is_loading`, `is_impersonating` and a deferred `verification_error` (the restored
session stays usable). `check_auth(None)` verifies the session against the server now;
`authenticate(token)` / `deauthenticate()` drive the socket with a token from outside the client.

## Live queries

Build a query on a table, then `live` registers it and subscribes in one call. The query stays
registered, and its rows live, while the returned `LiveQuery` does.

<CodeBlock code={queriesCode} lang="rust" />

A `LiveQuery` reads like a watch channel: the latest rows are always there, a slow consumer never builds
a backlog.

| Method | Returns |
| --- | --- |
| `rows()` | `Arc<Vec<Row>>`, the latest rows. `Row` is a `BTreeMap<String, Value>`. |
| `rows_as::<T>()` | The latest rows decoded into your `Deserialize` type. |
| `changed().await` | Waits for the next change; `Err(Error::Closed)` once the client is gone. |
| `status()` | `QueryStatus::Fetching` while bodies are being pulled, else `Idle`. |
| `is_authoritative()` | True once server membership is known. Only then does an empty list mean "empty". |
| `rows_watch()`, `status_watch()`, `authority_watch()` | The underlying `tokio::sync::watch` receivers. |
| `into_stream()` | The current rows, then every change, as a `futures::Stream`. |

Rows hold plain JSON shapes: record links are `table:id` strings and datetimes are ISO strings.

The builder covers filters, ordering, paging and joins. Conditions are AND-joined, one per field;
a repeated field replaces the earlier condition. String values for `record<..>` and `datetime` columns
are re-typed from the schema, so `where_eq("owner", "user:ada")` matches on the server.

<CodeBlock code={builderCode} lang="rust" />

`.related(field)` follows a relationship from the schema: a forward `record<x>` field joins one row
under the same name, the reverse direction joins a list. Use `.related_with(field, |q| q.limit(5))`
to shape the joined rows. `.one()` limits to one row, `.select([..])` projects fields.

### Raw SurrealQL

`live_raw` registers any `SELECT` the stream processor can run. Raw params are sent as given, so pass
record links as `RecordId` values. `QueryOptions::ttl` sets how long the server keeps the view after
the last subscriber leaves (`10m` by default).

<CodeBlock code={rawCode} lang="rust" />

`query_raw` registers without subscribing and returns the hash; `subscribe(hash)` attaches a
`LiveQuery` to it later. `preload_query(builder)` (or `preload(sql, params, options)`) prewarms a query:
it returns at once when the query resolved before on this device, otherwise once the server's
membership and every row are local. `query_remote(sql, vars)` is a one-shot server read that is not
synced into the local store: use it for counts and other reads a view cannot express.

## Writes

<CodeBlock code={writesCode} lang="rust" />

`create`, `update` and `delete` are optimistic: the row changes in the local store and in every live
query before the call returns, and the write is queued in the outbox, which is pushed in order in the
background and survives restarts. Record ids are full `table:key` strings; `spooky_core::value::generate_id()`
makes a fresh key.

Writes take anything `IntoObject`: a `serde_json::json!({..})` object, a `serde_json::Map`, or an
`Object`. `spooky_core::to_object(&value)` turns your own `Serialize` type into one. A `record<..>`
field may be given as its `table:id` string: the schema re-types it before it reaches the server.
`update` merges the given fields into the row. `read_row(id)` reads one row as the local store holds it.

### Debounced updates

For a text field saved as the user types, fold rapid updates into one outbox write:

<CodeBlock code={debounceCode} lang="rust" />

A debounced update applies locally at once, then writes the merged patch after the pause (300 ms by
default). By default one write is kept per record and set of fields (`DebounceKey::RecordIdXFields`);
`DebounceKey::RecordId` keeps one per record.

## Failed writes

A write the server rejects is undone locally and parked in a tray, so the app can show it and let
the user retry or drop it:

<CodeBlock code={trayCode} lang="rust" />

Each `FailedMutationRow` has the mutation type, the record id, the data, the row as it was before
(`before_record`), the error (`message` and `kind`), the attempt count and how much was reverted.
`retry_failed_mutation(id)` re-applies it as a new optimistic write; `discard_failed_mutation(id)` drops it.

## Sync indicators

Every indicator is a value you can read now plus a `tokio::sync::watch` receiver for every change
after. Watch receivers need no tokio runtime on your side, so they work on any executor.

| What | Now | Every change |
| --- | --- | --- |
| Sync health (the "can't reach the server" banner) | `sync_health()` | `sync_health_watch()` |
| Queued writes | `pending_mutation_count()` | `pending_mutations_watch()` |
| Queries a user waits on | `fetching_query_count()` | `fetch_activity_watch()` |
| Rejected writes | `failed_mutation_count()` | `failed_mutations_watch()` |
| Records with unacknowledged writes | `unsynced_record_ids()` | `unsynced_records_watch()` |
| Signed-in user / auth session | `user_id()` / `auth_state()` | `user_watch()` / `auth_watch()` |

<CodeBlock code={syncCode} lang="rust" />

`SyncHealth` has `status` (`Healthy` or `Degraded`), `consecutive_failures`, `kind` (`network` or
`application`) and `error` while degraded, `ever_connected`, and `connection` (the socket's own
state, independent of health). `client.events()` is a broadcast of every engine event
(records, statuses, mutations, health, logs) for diagnostics; a slow receiver skips.
See [Offline & sync health](/docs/client/offline-sync) for what each signal means.

## Buckets

<CodeBlock code={bucketsCode} lang="rust" />

`read` goes through the blob cache: a warm read never touches the socket. Give
`BlobCacheConfig::directory` a path to keep files on disk between runs; without one the cache is in
memory. Files never expire by age: the least recently used go past `max_bytes`, files are kept per
signed-in user, and `put` / `delete` on a path invalidate it. `get` always reads the server,
`evict(path)` drops the cached copy, and `client.blob_cache_stats()` reports hits, misses and size.
Buckets need a remote endpoint; see [File buckets](/docs/client/buckets) for defining them.

## Feature flags and releases

<CodeBlock code={flagsCode} lang="rust" />

`feature(key, fallback)` is live: `variant()` is the assigned variant, or the fallback while the user
has none, `enabled()` is true for any variant other than `off`, and `payload_as::<T>()` decodes the
flag's payload. `app_release(app)` watches the latest release announced for `app`; `update_available`
compares it with your version. Both need a remote endpoint and stay live while the handle lives. See
[Feature flags](/docs/client/feature-flags) and
[Telling clients a new version shipped](/docs/client/offline-sync#telling-clients-a-new-version-shipped).

## Backend jobs

`run(backend, path, payload, options)` enqueues a job for a backend: a row in the backend's outbox table,
written through the same optimistic path as any other write, so it queues while offline.

<CodeBlock code={jobsCode} lang="rust" />

The backend must be in the client schema. Pass its OpenAPI spec to codegen, which also generates a
typed method per route (`app.run().api().spookify(..)`): required args are plain parameters,
optional ones `Option`s.

<CodeBlock fileName="build.rs" code={backendsBuildCode} lang="rust" />

`RunOptions` sets `assigned_to`, `max_retries`, `retry_strategy`, `timeout` and `delay` (ms). See
[Add a backend](/docs/backend/add) for the server side.

## Peer to peer channels

<Experimental>
  Channels are experimental. The Rust client speaks the same wire protocol as the web and Flutter
  clients, so all three connect to each other.
</Experimental>

Tables marked `-- @channel` can carry writes straight between devices over WebRTC, so a peer's change
(a cursor, a chat message, a move) shows up before the server has it. The core has no WebRTC stack of
its own: the app adapts one (webrtc-rs, libwebrtc bindings, ...) to the `RtcPeerConnection` and
`RtcDataChannel` traits in `spooky_core::modules::channel` and hands the factory in through the config.
Without a factory (or a custom `transport`) channels report `ChannelStatus::Unsupported`.

<CodeBlock code={channelsConfigCode} lang="rust" />

Open a channel with the queries whose rows it carries and the users it connects to. Only the queries'
`where` counts, evaluated against each row; they are never registered. A connection forms only when
both sides list each other, your own id is skipped, and the transport starts once a user is signed in.

<CodeBlock code={channelsCode} lang="rust" />

Plain `client.update(..)` on a matching row reaches the peers of every open channel whose filter the
row matches; `channel.create/update/delete` reach that channel's peers only. `-- @ephemeral` fields
travel between peers and never reach the database. The channel closes when dropped.
`channel.set_peers(..)` and `channel.set_queries(..)` change it in place. See
[Peer to peer channels](/docs/client/channels) for the model, accept rules and TURN servers.

## Native push

<Experimental>
  Native push is experimental. The core registers the device with the server; getting the device
  token from APNs or FCM is up to the app.
</Experimental>

<CodeBlock code={pushCode} lang="rust" />

Call `client.push()` once at startup: the first call installs the sign-out hook that unregisters this
device while the session is still valid. `register` stores the device for the signed-in user and
remembers the choice; `sync` (call it on every launch) brings the server in line after a token rotation
and never fails, it answers a `PushSyncStatus`. `unsubscribe(all)`, `update(changes)`, `devices()`,
`notify(message)`, `cancel(id)` and `test(title, body)` cover the rest. Errors are `PushError` with a
`code` (`SignedOut`, `Disabled`, `NotSubscribed`, `Server`, ...). A client without an endpoint answers
every call with `PushErrorCode::Server`. See [Native push](/docs/client/native-push) for the server setup.

## Lifecycle

The core cannot see the network or the app's lifecycle, so the app reports both:

<CodeBlock code={lifecycleCode} lang="rust" />

- `wake()` on a resume or a returning network: reset the reconnect backoff and probe the socket now.
- `set_offline(true)` when the OS reports no network: a `preload` that never resolved on this device
  returns at once instead of waiting for the server, so an app holding its first screen on it still opens.
  Report it before the first `preload`.
- `checkpoint().await` when the app goes to the background: snapshots the circuit so the next boot
  restores it instead of re-reading every row. The client also checkpoints on its own (5 s after boot,
  then every `circuit_checkpoint_ms`), and it is free when nothing changed.
- `detach().await` when this install goes away for good: hands its views back to the server instead of
  leaving them to expire.
- `close().await` before the process exits.

<Warning>
  Dropping the last `Sp00kyClient` handle closes the client in the background, and a process that exits
  right after may kill the engine thread before the snapshot is written. Await `client.close()` before
  `main` returns.
</Warning>

## GPUI and other executors

The engine never runs on your executor. `Sp00kyClient` talks to its thread over a channel, so any
async runtime can await it, and a UI thread never blocks on sqlite or the socket. In GPUI, hold the
client in your app state and pump a `LiveQuery` from a foreground task:

<CodeBlock fileName="src/notes_view.rs" code={gpuiCode} lang="rust" />

The same works with no async runtime at all:

<CodeBlock fileName="src/main.rs" code={blockOnCode} lang="rust" />

`client.live(..)` returns a `Send + 'static` future, so you can build it on one thread and await it on
another. A `LiveQuery` is `Send` too: hand it to a background task with `tokio::spawn` if that is
where your app lives.

## The in-process engine

`spooky_core::Engine` is the engine itself, without the thread: single-threaded on a tokio `LocalSet`,
with the same calls returning non-`Send` futures and callback subscriptions. Use it when you already own
a `LocalSet` (tests, embedding in a single-threaded runtime).

<CodeBlock fileName="src/main.rs" code={engineCode} lang="rust" />

`Engine::open` returns an `Rc<Engine>`. Its builder is bound to the engine, so `query(..).run(ttl)`
registers and `query(..).subscribe(ttl, cb)` registers and watches in one call; `TypedQuery::watch`
works the same way. Writes take an `Object` (use `object_from_json(json!(..))`), `close()` returns
nothing, and the generated `AppDb` drives `Sp00kyClient` only.

export const gpuiCode = `use gpui::Context;
use spooky_core::Sp00kyClient;

use crate::db::Note;

pub struct NotesView {
    client: Sp00kyClient,
    notes: Vec<Note>,
}

impl NotesView {
    fn watch_notes(&mut self, owner: String, cx: &mut Context<Self>) {
        let live = self.client.live(self.client.query("note").where_eq("owner", owner));
        cx.spawn(async move |this, cx| {
            let Ok(mut live) = live.await else { return };
            loop {
                let notes = live.rows_as::<Note>().unwrap_or_default();
                let alive = this.update(cx, |view, cx| {
                    view.notes = notes;
                    cx.notify();
                });
                // Stop when the view is gone or the client closed.
                if alive.is_err() || live.changed().await.is_err() {
                    break;
                }
            }
        })
        .detach();
    }
}`;
