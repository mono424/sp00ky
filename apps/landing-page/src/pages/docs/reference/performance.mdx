Imagine a chess library with **100,000 games**. You show **50 games at a time**,
scroll through the library, rename players, and import more games. This page
shows how long those actions took in our benchmark.

**“Ready” means the server's published list passed our data checks.** Downloading
and drawing the list in a browser were outside the test.

## WhitePawn benchmark

Here are the results in everyday terms:

- **Open a 50-game list:** typically **0.17–0.38 seconds** in a 100,000-game library.
- **Change a game or player:** typically **0.06–0.15 seconds** until the published
  result reflected the change.
- **Import 30,000 games:** **30 seconds** to write them, then **8–12 seconds**
  to check that the retained lists had caught up.
- **Start with 100,000 games already seeded:** about **9–16 seconds** until the
  scheduler and SSP were ready.

The two 100,000-game runs use the same dataset. We call them **100K A** and
**100K B** so you can see how results varied. A ran in the standard profile;
B repeated the case in the large profile. They ran on a shared development
machine, and their samples are kept separate.

<Note>
These are **October 11, 2026 measurements of canary.301**, before the newer
index-building and batching improvements. They are a recorded baseline;
we have not rerun this workload to measure those improvements yet.
</Note>

## Import 30,000 games

**Example:** “I start with 100,000 games and import 30,000 more at 1,000 games
per second. The database accepts all 30,000 in **30 seconds**. After the import
ends, the benchmark needs about **12 more seconds** in run A, or **8 more
seconds** in run B, to check the source and confirm the retained lists have
caught up.”

That extra time has two parts. First the benchmark reads the database to work
out what each list should contain. Then it waits for the published lists to
match. Sync continues during both parts.

| Test | Time | Games added | Games/second |
| --- | ---: | ---: | ---: |
| Steady | 60 s | 3,000 | 50 |
| Import | 30 s | 30,000 | About 1,000 |

Both 100K runs had **zero failed writes** in these phases. Imports used 100-game
transactions, with at most four transactions running at once. The achieved rate
measures database commits; it does not mean every list updates 1,000 times per
second. Across these completed runs, the publication queue's sampled peak was
about 12 MiB. Full queue measurements are in the detailed results below.

## What about one million or ten million games?

**We do not have measured results for those sizes.** The benchmark's resource
checks stopped them before startup on this machine.

- **10,000 games:** completed with and without move text.
- **100,000 games:** completed twice.
- **1 million games:** resource-limited, with and without move text; not run.
- **10 million games:** resource-limited; not run.

The machine had 36 GiB RAM and a 15.66 GiB Docker memory budget. The checks keep
memory and disk headroom, using smaller completed tests to estimate larger ones.
A resource-limited result is a capacity estimate, rather than an observed crash.
The standard and large commands therefore exited nonzero, while retaining their
successful 100K results.

## Make a large library easier to query

**Example:** “Show the next 50 games from this collection, in their saved order.”
An index on the collection and sort field lets the engine look up the matching
range. Think of finding a chapter in a book's index instead of reading every
page from the beginning.

Here `database` means the game collection. Bind `$database` to its
`game_database` record. `LIMIT 50` returns fifty rows; `START 100` skips the
first hundred. The final `id` makes tied sort values deterministic.

Newer releases build a first-use index in short steps so writes can run between
steps. They also group already queued changes into batches. These changes can
reduce repeated work, but this page's WhitePawn measurements predate them.
There is no measured WhitePawn speedup to quote yet.

<details>
<summary>More about indexes, batching and engine-only measurements</summary>

An indexed window needs equality filters on the index's leading fields, followed
by matching sort fields. An unrelated filter or a range comparison on its own
does not get the same shortcut. Full-text, vector and count indexes are not used
for this list lookup.

A historical [Rust engine experiment](https://github.com/mono424/sp00ky/commit/80ec1dc2c95b4e084f4de1472cd2d27345f79a24)
registered twenty windows over one million rows in **14.6 seconds without the
index** and **0.58 seconds with it**, including the first build. The fixture has
420,000 rows in the selected collection. This measured in-process engine
registration; it did not include a database changefeed, publication or a browser.

Indexes are built when needed, kept for an hour after their last view leaves,
and prewarmed for restored active views before the SSP reports ready. Schema
changes prewarm replacements too. A live first build still scans its table, but
targets 25 ms per step and releases the circuit between steps. Writes
keep an unfinished index correct; queries only read it once complete. A separate
one-million-row test reduced the longest lock hold from 0.88 seconds to 74 ms,
while the complete build took about twice as long. These are engine observations,
not the WhitePawn publication times above.

The scheduler batches already queued ordinary changes up to **128 records or
1 MiB**, without waiting to fill a batch. The SSP applies their source changes
in order and updates affected query computations once per batch. Older SSPs,
replay, jobs, users and internal lifecycle records keep their single-record paths.

For implementation details, see [registration and ingest stages](/docs/reference/ssp-api#registration-and-ingest-stages)
and [batch ingestion](/docs/reference/ssp-api#post-ingestbatch). Rust embedders can
use `prewarm_query_indexes`, `prewarm_active_indexes`, `prewarm_index` and the
step-based variants. Their `IndexBuildStats` report index count, rows indexed
and build time. Query stage timings are shared measurements for affected views,
rather than exclusive CPU costs for each view.

Slow-operation evidence, publication wait times and queue diagnostics are
explained in the [SSP API](/docs/reference/ssp-api#publication-isolation-and-latency)
and [scheduler API](/docs/reference/scheduler-api). Permission-join maintenance
still costs work proportional to the set of records a changed join key affects.

</details>

## How to read these results

The WhitePawn tests ran on October 11, 2026 with an Apple M3 Max, 14 cores,
36 GiB RAM, macOS arm64, Node 22.22.3 and Docker 29.4.0. Other development
containers were running. The measured release binaries were version
`0.0.1-canary.301`; SurrealDB was 3.1.5.

The data is synthetic: twenty collections, 256 players and 80% of games in one
large collection. Games share sort values, and each list joins the white and
black player records. The full-move fixture adds about 1.2 KiB of text per game.

Publication checks verify the expected game/player references, parent links and
required record versions. They do not compare every projected field or prove
published edge order. Initial `ready` status alone is insufficient. Browser
rendering, client downloads, production authorization, background jobs and
multiple SSPs are outside these tests.

export const listCode = `-- Index: collection first, then the field used to sort.
DEFINE INDEX game_database_sort ON TABLE game FIELDS database, sort_index;

-- Read games 101 to 150 from one collection.
SELECT id, date, result, eco, sort_index
FROM game
WHERE database = $database
ORDER BY sort_index ASC, id ASC
LIMIT 50 START 100;`;
