Performance

How long does a list take to update? Measured examples, simple graphs, and commands to try it yourself.

Imagine a chess library with 100,000 games. You show 50 games at a time, scroll through the library, rename players, and import more games. This page shows how long those actions took in our benchmark.

“Ready” means the server’s published list passed our data checks. Downloading and drawing the list in a browser were outside the test.

WhitePawn benchmark

Here are the results in everyday terms:

  • Open a 50-game list: typically 0.17–0.38 seconds in a 100,000-game library.
  • Change a game or player: typically 0.06–0.15 seconds until the published result reflected the change.
  • Import 30,000 games: 30 seconds to write them, then 8–12 seconds to check that the retained lists had caught up.
  • Start with 100,000 games already seeded: about 9–16 seconds until the scheduler and SSP were ready.

The two 100,000-game runs use the same dataset. We call them 100K A and 100K B so you can see how results varied. A ran in the standard profile; B repeated the case in the large profile. They ran on a shared development machine, and their samples are kept separate.

Note

These are October 11, 2026 measurements of canary.301, before the newer index-building and batching improvements. They are a recorded baseline; we have not rerun this workload to measure those improvements yet.

Open a list of 50 games

Example: “There are 100,000 games in my library. I scroll to a new page of 50 games. The server publishes that page in about 0.17 seconds in run A, or 0.38 seconds in run B.”

The graph also shows two smaller tests. 10K + moves stores synthetic chess move text as well as game metadata; the list itself still requests only the small summary and player names.

p50 is the middle result: half the measurements finished within that time. p95 is the time within which 95% finished. A shorter bar means less waiting. All values below are in seconds.

Each case scrolled 100 times, with at most twenty lists retained at once. There were 99 new registrations and one visit to an already retained list. These times start before registration and include the response and publication check; they do not stop at the first HTTP response.

Change a game or rename a player

Example: “I rename a player in a 100,000-game library. The server’s list is ready with the updated player record in about 0.05 seconds in run A, or 0.14 seconds in run B.”

Other changes take different amounts of work. These are the typical times (p50) for three concrete actions:

The next graph combines all seven kinds of change: insert, edit, reorder, move between collections, delete, rename a player, and write to another collection. Each full run has 140 measurements, taken one change at a time.

Saving to the database finishes earlier. For example, run A’s typical database acknowledgement was 0.003 seconds, while the published result check took 0.063 seconds. The latter already includes the write time.

Import 30,000 games

Example: “I start with 100,000 games and import 30,000 more at 1,000 games per second. The database accepts all 30,000 in 30 seconds. After the import ends, the benchmark needs about 12 more seconds in run A, or 8 more seconds in run B, to check the source and confirm the retained lists have caught up.”

That extra time has two parts. First the benchmark reads the database to work out what each list should contain. Then it waits for the published lists to match. Sync continues during both parts.

Add the two bars for each run to get the roughly 12- or 8-second confirmation time. The remaining-wait bar alone does not measure the whole delay after the import. This checks the retained lists, rather than every possible query.

Both 100K runs had zero failed writes in these phases. Imports used 100-game transactions, with at most four transactions running at once. The achieved rate measures database commits; it does not mean every list updates 1,000 times per second. Across these completed runs, the publication queue’s sampled peak was about 12 MiB. Full queue measurements are in the detailed results below.

Start with an existing library

Example: “My 100,000 games are already in the database. Starting the scheduler and SSP takes about 9 seconds in run A or 16 seconds in run B before the backend is ready.”

The scheduler reads and distributes changes. The SSP maintains the live query results. This graph includes starting both services and waiting for an available SSP.

These are single startup observations. Database startup and creating the test data are separate: seeding the 100,000 games took about 15 seconds in A and 22 seconds in B.

How much memory did it use?

Example: “During the 100,000-game test, the scheduler peaked at about 1.1 GiB and the SSP at about 0.76 GiB. The database container used another 1.2–1.3 GiB at its sampled peak.”

The graph covers the scheduler and SSP; the database is additional. These are separate peaks across the whole test and may have occurred at different times. The database and replica files occupied about 0.92 GiB on disk after each 100K run. CPU, database memory and detailed storage figures are available below.

Even a 50-row list needs more memory than its fifty displayed rows. The SSP also holds source records, indexes and the state used to maintain the query.

What about one million or ten million games?

We do not have measured results for those sizes. The benchmark’s resource checks stopped them before startup on this machine.

  • 10,000 games: completed with and without move text.
  • 100,000 games: completed twice.
  • 1 million games: resource-limited, with and without move text; not run.
  • 10 million games: resource-limited; not run.

The machine had 36 GiB RAM and a 15.66 GiB Docker memory budget. The checks keep memory and disk headroom, using smaller completed tests to estimate larger ones. A resource-limited result is a capacity estimate, rather than an observed crash. The standard and large commands therefore exited nonzero, while retaining their successful 100K results.

Make a large library easier to query

Example: “Show the next 50 games from this collection, in their saved order.” An index on the collection and sort field lets the engine look up the matching range. Think of finding a chapter in a book’s index instead of reading every page from the beginning.

-- Index: collection first, then the field used to sort.
DEFINE INDEX game_database_sort ON TABLE game FIELDS database, sort_index;

-- Read games 101 to 150 from one collection.
SELECT id, date, result, eco, sort_index
FROM game
WHERE database = $database
ORDER BY sort_index ASC, id ASC
LIMIT 50 START 100;

Here database means the game collection. Bind $database to its game_database record. LIMIT 50 returns fifty rows; START 100 skips the first hundred. The final id makes tied sort values deterministic.

Newer releases build a first-use index in short steps so writes can run between steps. They also group already queued changes into batches. These changes can reduce repeated work, but this page’s WhitePawn measurements predate them. There is no measured WhitePawn speedup to quote yet.

More about indexes, batching and engine-only measurements

An indexed window needs equality filters on the index’s leading fields, followed by matching sort fields. An unrelated filter or a range comparison on its own does not get the same shortcut. Full-text, vector and count indexes are not used for this list lookup.

A historical Rust engine experiment registered twenty windows over one million rows in 14.6 seconds without the index and 0.58 seconds with it, including the first build. The fixture has 420,000 rows in the selected collection. This measured in-process engine registration; it did not include a database changefeed, publication or a browser.

Indexes are built when needed, kept for an hour after their last view leaves, and prewarmed for restored active views before the SSP reports ready. Schema changes prewarm replacements too. A live first build still scans its table, but targets 25 ms per step and releases the circuit between steps. Writes keep an unfinished index correct; queries only read it once complete. A separate one-million-row test reduced the longest lock hold from 0.88 seconds to 74 ms, while the complete build took about twice as long. These are engine observations, not the WhitePawn publication times above.

The scheduler batches already queued ordinary changes up to 128 records or 1 MiB, without waiting to fill a batch. The SSP applies their source changes in order and updates affected query computations once per batch. Older SSPs, replay, jobs, users and internal lifecycle records keep their single-record paths.

For implementation details, see registration and ingest stages and batch ingestion. Rust embedders can use prewarm_query_indexes, prewarm_active_indexes, prewarm_index and the step-based variants. Their IndexBuildStats report index count, rows indexed and build time. Query stage timings are shared measurements for affected views, rather than exclusive CPU costs for each view.

Slow-operation evidence, publication wait times and queue diagnostics are explained in the SSP API and scheduler API. Permission-join maintenance still costs work proportional to the set of records a changed join key affects.

Run it yourself

From the repository root, with Docker running:

# Build the services and benchmark once.
cargo build --release -p sp00ky-cli -p scheduler -p ssp-server
docker pull surrealdb/surrealdb:v3.1.5
pnpm -F @spooky-sync/benchmark build

# Quick check: two 10,000-game cases.
node apps/benchmark/dist/index.js whitepawn --smoke

# Larger datasets and full-length write phases.
node apps/benchmark/dist/index.js whitepawn --profile standard
node apps/benchmark/dist/index.js whitepawn --profile large

The smoke test runs both 10K datasets and short write phases. Standard attempts 100K and 1M cases. Large also attempts 10M. Each case gets a fresh, disposable, disk-backed SurrealDB 3.1.5 instance and one scheduler/SSP pair.

These commands save summary.md, samples.json and run.json under results/whitepawn-<timestamp>/ in the repository root. Completed results survive a later failure. See the benchmark CLI reference for custom binaries, output paths and the 3,600-second per-wait startup/readiness timeout.

How to read these results

The WhitePawn tests ran on October 11, 2026 with an Apple M3 Max, 14 cores, 36 GiB RAM, macOS arm64, Node 22.22.3 and Docker 29.4.0. Other development containers were running. The measured release binaries were version 0.0.1-canary.301; SurrealDB was 3.1.5.

The data is synthetic: twenty collections, 256 players and 80% of games in one large collection. Games share sort values, and each list joins the white and black player records. The full-move fixture adds about 1.2 KiB of text per game.

Publication checks verify the expected game/player references, parent links and required record versions. They do not compare every projected field or prove published edge order. Initial ready status alone is insufficient. Browser rendering, client downloads, production authorization, background jobs and multiple SSPs are outside these tests.

Write rate and catch-up

Full cases write 3,000 rows at a target of 50 rows/s for 60 seconds, then import 30,000 rows at a target of 1,000 rows/s for 30 seconds. Imports use 100-row transactions with at most four in flight. Smoke runs each phase for two seconds, committing 100 and 2,000 rows respectively. All completed cases had zero failed load-phase rows.

Throughput counts committed source rows per write interval. It does not establish the rate at which the SSP publishes them. After writes finish, the driver reads expected source windows, then times residual publication catch-up. The pipeline can drain while those source queries run, so the two durations below must be read together; residual catch-up alone is not total propagation delay.

Graph sharing and memory attribution

With view sharing enabled, adding the identical subscriber kept graph count at 17 and increased merged followers from 0 to 1 in every case. A follower shares another registration’s computation; the graph owner is excluded from the follower count. After import, the smoke cases retained sharing, while both 100K cases had nineteen independent graphs and zero merged followers. Later memory observations include that change in graph sharing.

In these reports, neither 1M case nor the 10M case ran. The standard run excluded 1M compact on projected host memory and 1M PGN on projected disk, host memory and Docker memory. Older tests that measure the engine without the full sync path

These May 1, 2026 microbenchmarks start at POST /ingest and stop when the SSP’s in-memory result hash changes. They bypass database write acknowledgement and changefeed transport, and do not measure durable publication or client visibility. They should not be compared directly with the WhitePawn times.
