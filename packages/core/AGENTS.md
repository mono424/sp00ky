# `@spooky-sync/core` — agent guide

## What this package is

The sync engine. A `Sp00kyClient<S>` owns a local database (memory or IndexedDB), a remote SurrealDB connection, a mutation queue, and a CRDT manager. It's framework-agnostic — UI bindings live in `@spooky-sync/client-solid`, `client-solid2`, `client-react`, `client-svelte` and `client-angular`. Most app code touches this package indirectly through a UI binding's `useDb()` hook.

## Mental model

```
.surql schema
   │  spky generate
   ▼
schema.gen.ts (typed schema + SURQL_SCHEMA constant)
   │  passed to Sp00kyConfig
   ▼
Sp00kyClient<S>  ── facade: every method = one saga run, selector or subscription
       │
       ├── Runtime (client/runtime.ts): one immutable ClientState, lanes, timers,
       │     subscriptions, dirty -> materialize scheduling. `query:status`,
       │     `activity:changed` and `health:changed` are all notified from here,
       │     off state transitions - never emitted by a saga, so a change made
       │     outside a sync round (a socket drop, say) still reaches subscribers
       ├── Sagas (query/ mutation/ sync/ boot/): pure generators yielding effects
       └── Interpreter (kernel/interpreter.ts) -> adapters (services/):
             local store · remote socket · SSP wasm circuit · tabs broker · blobs
```

Local writes are applied optimistically (row + outbox entry in one local
transaction), rendered through the outbox overlay, and drained to the remote in
FIFO batches. Each statement of a batch commits on its own, but the server stops
the batch at its first failed statement (`remoteBatch` chains them), so no write
reaches the server ahead of an earlier one that failed. A batch whose answer is
lost (it threw a transport error, or its rows were loaded from the store after a
restart) is in doubt (`OutboxItem.inDoubt`): re-sent, an in-doubt CREATE checks
the row already on the server and is a no-op when it holds what the CREATE
writes. Server membership arrives through one batched edge read (registration,
poll, LIVE dirt) and bodies are fetched once across all queries. Rows are always
re-materialized from state, never patched in place.

## Key exports (`src/index.ts`)

- `Sp00kyClient<S>` — main class. Methods: `init()`, `create(id, payload)`, `update(table, id, payload, options?)`, `delete(table, id)`, `query(table, opts?)`, `preload(query, { signal? })`, `run(backend, route, payload)`, `bucket(name)`, `remoteQuery(sql, vars?)`, `useRemote(fn)`, `authenticate(token)`, `auth.signOut()`. Admin impersonation (`impersonation.enabled` in sp00ky.yml, admins only, server-enforced): `auth.impersonate(targetId, reason)`, `auth.stopImpersonating()`, `auth.impersonation`, `auth.subscribeImpersonation(cb)`, `auth.searchImpersonationTargets(search)`; while active the client injects a warning bar with a Stop button and shifts the page down onto a hazard-striped layer. `impersonationBanner` in the client config restyles it (`theme`), replaces it (`mode: 'custom'` + `client.acknowledgeImpersonationBanner()`, else it falls back after ~2.5s) or turns it off (`mode: 'none'`). See `/docs/client/impersonation`. Traffic indicators: `pendingMutationCount` / `subscribeToPendingMutations(cb)` (outbox depth), `fetchingQueryCount` / `subscribeToFetchActivity(cb)` (queries a user waits on; a query that already shows rows and is only re-registering, as after a reload, is not counted). Failed-writes tray: `failedMutationCount`, `subscribeToFailedMutations(cb)`, `listFailedMutations()`, `retryFailedMutation(id)`, `discardFailedMutation(id)`.
- `FailedMutation` — a row of the `_00_failed_mutations` tray (`mutationType`, `recordId`, `data`, `beforeRecord`, `error`, `revert`).
- `BucketHandle` — file storage handle (`put`, `get`, `delete`, `exists`), plus the cache-aware `read`, `url`, `pin`/`unpin`, `evict`, `prefetch`. `get` is always remote; `read`/`url` go through the blob cache. A bucket generated with `backend: 'r2'` (`BACKEND "r2"`) sends its bytes to the SSP over HTTP (`<files.endpoint>/bucket/<name>/<path>`, bearer = the session token from `RemoteDatabaseService.getAuthToken()`) instead of `f"bucket:/path"` statements; the SSP checks `fn::_00_bucket::<name>` as the user first.
- `services/blobs/` — durable cache for bucket bytes: OPFS holds the files, `_00_blob` holds a manifest that reconcile rebuilds from disk (so a wiped local store costs metadata, not the offline cache). Nothing expires on a timer; eviction is LRU under a byte budget only, skipping pinned and on-screen entries. Config: `blobCache` in `types.ts`.
- `AuthService` — token management, sign-in/sign-out events. `subscribe(cb, { immediate? })` calls `cb` at once with the current user unless `immediate: false`, then on every change.
- `CrdtManager`, `CrdtField`, `cursorColorFromName`, `CURSOR_COLORS`: collaborative `@crdt` fields on Loro. Client methods: `openCrdtField(table, recordId, field, draft?)` -> `Promise<CrdtField>` (every open of one field in a tab shares one `LoroDoc`; pair each with a close), `closeCrdtField(table, recordId, field)` -> `Promise<void>` (resolves once unsent edits are in the outbox; offline, once they are saved on the device, never waiting on the network), `createCrdtDraft(table, field)` -> a detached `CrdtField` for a record not created yet (`db.create` first, then pass it to `openCrdtField` as `draft`). `CrdtField`: `getDoc()`, `hasContent()`, `pushCursorState(bytes)`, `onCursorUpdate = cb` (a setter). Config: `crdt: true` preloads Loro, `crdtDebounceMs` (the first edit after a quiet spell waits this long, default 50), `crdtSendIntervalMs` (shortest gap between two sends of one field while typing, default 200). Design: `docs/crdt-v2.md` at the repo root.
- **Peer to peer channels** (`-- @channel` tables, experimental): `client.channel(query, peers)` (a query builder, a built query, or a list, on `@channel` tables; typed from the query; own id skipped; both sides must list each other) opens WebRTC data channels to the peers' tabs and returns `Sp00kyChannel` (`state()`, `subscribe(cb)`, `setPeers`, `setQueries`, `close`, `tables()`, plus scoped `update` / `create` / `delete`). Only the query's `where` counts (`matchesWhere`, pure JS over the plan; `compileScope` throws for `.related()`, link-following paths, `$params`, unknown ops); it is never registered. `orderBy` / `limit` / `offset` / `select` / `.one()` warn once per shape (`unusedArgs`) unless the builder has `.ignoreUnusedArgs()`. Writes go to the peers of every open channel whose filter the row matches: a create checks the new row, an update or delete the stored row (`readRow` saga) before and after the patch. A peer's write is taken only if the sender is listed by a channel whose filter the row matches (an update/delete of a row not held is ignored). Peers fold updates into every subscription showing the row (output only, never the store): normal fields retire once the synced row holds them (or after `channels.confirmTimeoutMs`, default 5000); `-- @ephemeral` fields (optional, never filtered on) never reach the database, last writer wins, vanish when their author disconnects. A peer's create goes into the store and circuit like an own optimistic create minus the outbox (`peerCreate` saga, `state.peerWrites` folded into `overlay()`) and is undone at `confirmTimeoutMs` unless the server body landed (`versions`); a peer's delete hides the row through the overlay until it expires (`peerDelete`, `PeerWriteExpired`). Signaling is raw CREATE/LIVE on the generated server-only `_00_channel_signal` (sender stamped by the DB). Everything beyond identity, filter and field types is `channels.accept: { [table]: ({ kind, from, table, id, row, patch }) => boolean }`. Config also `iceServers`, `transport`. **Sharing with the user's own devices** (`channels.share`, needs `channels.relay`; Dart and Rust have the same on the same wire): `share: { tables: { game: true, note: (row) => !row.draft } }` sends the user's own optimistic writes on those tables (no `-- @channel` needed) to their other devices, which treat them like any peer's write. `ChannelManager` keeps one internal channel whose only user is the signed-in one (`sharing`, `ownState()`, `subscribeOwn`; facade: `client.shareState()`, `client.subscribeShareState(cb)`). Transport: `splitTransport(room, mesh)` routes the own user to the room and everybody else to the WebRTC mesh. The room is `hubTransport` (`modules/channel/hub.ts`: one link per browser, a Web Lock picks the tab that holds it, the others reach it over a `BroadcastChannel`; hubs tell each other which tabs they speak for, so a peer is still one tab; tabs of one browser are not peers) over `roomLink` (`modules/channel/room.ts`: a WebSocket to `sp00ky-relay`, protocol in `apps/relay/README.md`, hello with the session token, reconnect with backoff, plus a direct WebRTC link signaled through the relay while exactly two browsers are in the room). Interest: each tab tells the user's other tabs what its subscriptions can show (`client.subscribe` passes `channels.interestOf(def.plan, def.params)` to `tap`; `queryInterest` / `mergeInterest` / `showsRow`, wire message `{ t: 'interest' }`, only ever between tabs of one user), and `send` skips a tab that shows nothing of the row; a filter the row alone cannot decide, or a table read through `.related()`, counts as the whole table. A native client (Dart `spooky_core` `modules/channel/room.dart`, Rust `core-rs` `modules/channel/room.rs`) is a hub with one tab and no direct link; a change to the relay frames, the hub envelope (`{ h: 'tabs' }`, `{ h: 'm' }`) or the interest message needs all three clients. Dart has the same feature on the same wire protocol (`spooky_core` `modules/channel/`, `client.channel(...)`, WebRTC via `spooky_flutter`'s `flutterWebRtc`), so web and Flutter peers interoperate: keep the message shape, signaling rows and offer/answer ordering in step across both. Code: `modules/channel/`. Docs: `/docs/client/channels`.
- Types: `Sp00kyConfig` (client-solid wraps it as `SyncedDbConfig`), `QueryTimeToLive`, `PersistenceClient`, `StoreType`, `UpdateOptions`, `RunOptions`, `PreloadOptions`.
- Subpath: `@spooky-sync/core/otel` — `createOtelTransmit(endpoint)` for piping pino logs to OpenTelemetry.
- `client.webPush` (`WebPushModule`, `db.webPush` in the Solid bindings) - Web Push on the page: `support()`, `info()`, `subscribe(opts)` (call from a click), `unsubscribe(opts)`, `sync()`, `isSubscribed()`, `update(opts)`, `devices()`, `notify(msg)`, `cancel(id)`, `test()`, `bridge()`, `onMessage(cb)`. Server calls are `fn::push::*`; typed `WebPushError`; config `webPush` in `types.ts`. Sign-out runs through `AuthService.onBeforeSignOut`.
- Subpaths for service workers, workers and Node (no wasm, no pino, no DOM; `scripts/check-worker-entries.mjs` enforces it in `build`): `@spooky-sync/core/pure` (protocol builders), `@spooky-sync/core/live` (`createLiveFeed`, the live subscriber over the pure-JS SDK; a feed that shares views with another through the same `sessionId` must also pass the same `ownerSecret`, or a signed-out feed's second registration is refused 409 `owner_mismatch`), `@spooky-sync/core/sw` (`installPushHandlers`, `getBridgedToken`). Built by the second tsdown config; chunks are prefixed `worker-`. See `docs/web-push-design.md` at the repo root.

## Common gotchas

- **Use UI hooks, not the client directly.** In a Solid app, call `useDb()` from `@spooky-sync/client-solid`. Touch `Sp00kyClient` only inside `provider.client` for advanced flows.
- **Mutations are optimistic.** `db.create` / `db.update` / `db.delete` return immediately; the queue drains in the background. Inspect progress via `pendingMutationCount`.
- **Record IDs are full strings.** `db.create('thread:abc123', {...})` — *not* `db.create('thread', { id: 'abc123' })`. The first arg is `'<table>:<id>'`. Generate IDs with `Uuid` from `surrealdb` (re-exported by `client-solid`).
- **`db.update` takes `(table, id, payload, options?)`**. The `debounced` option (`{ debounced: true }` or `{ debounced: { delay, key, flushOnHide } }`) coalesces rapid updates, e.g. a plain text input saved as you type (never for `@crdt` fields, which are not written with `db.update`). With `flushOnHide` (default `true`) the merged patch is also kept in the local `_00_pending_writes` table and pushed as soon as the page is hidden, so a reload or closed tab inside the delay does not lose it (the next boot moves a leftover patch into the outbox). `flushOnHide: false` keeps the patch in memory only.
- **`db.remoteQuery(sql, vars?)` is the one-shot remote read.** It runs one SurrealQL statement through the client's remote path (connect gate, per-statement timeout, concurrency limit) and returns the SurrealDB result array; results are not synced into the local cache. Use it for counts and other reads the query builder can't express.
- **`db.useRemote(fn)` hands out the bare SDK client.** Same cache bypass, but it skips the connect gate (a call during a reconnect fails with "Specify a namespace to use"). Reserve it for SDK features `remoteQuery` cannot reach (transactions, `live`).
- **Raw remote calls are gated by the query allowlist.** When the generated schema carries `policy.queryAllowlist: 'warn' | 'enforce'` (from `sync.queryAllowlist` in `sp00ky.yml`), `remoteQuery`, `useRemote` and `queryRaw` throw unless the client config sets `allowRawRemote: true`; builder queries are unaffected. A registration the SSP refuses as not allowlisted (403 `not_allowlisted`) is marked `remote: 'failed'` after one attempt with an error-level log carrying the surql and a `spky generate` hint; the view stays cold (`membershipKnown` false), it is never read as confirmed empty.
- **A `@crdt` field is server-written plain text.** Edit it only through `openCrdtField` / `useCrdtField`; set it only in the `db.create` that makes the record (its initial text; a later client write keeps the old value). Reading it (lists, search, `where`) is fine, but it trails live edits until the SSP folds the edit log (a few seconds after the last edit by default). Edits travel as `<table>__crdt_log` rows through the ordinary outbox; each tab claims a random Loro peer in `_00_crdt_peer`, and log rows whose blob is not an update made by that peer are refused everywhere (`modules/crdt/acceptance.ts`, mirrored in Rust). Unsent edits survive reloads in `_00_crdt_local`. Dart (`spooky_core`) does not implement CRDT fields yet.
- **`@parent` columns are auto-populated.** Defined in the `.surql` schema as `record<user>` with the `-- @parent` annotation; never write them yourself — they're set from the auth context server-side.
- **`db.preload` is a registered query.** Resolved before on this device (a `_00_view` row exists) it returns at once; never resolved it waits until the server's membership and every body are local. A signed-out session without `enableAnonymousLiveQueries` is never sent membership, so its preload returns at once instead of blocking. It holds no subscriber, so it is evicted a ttl after registration unless a view mounts the same query. `refresh`/`staleTime` are ignored; pass `signal` to abort a cold wait.
- **A never-resolved query paints only vouched rows.** Before the server answers (`cold`), the local predicate scan shows a cached body only if some `_00_view` row names it (as a member or subquery child) or a write for it is in flight. A body no view names is an orphan (deleted upstream while nothing watched it): it stays hidden, and the GC deletes it 30 s after boot and then hourly. A `_00_view` row no query has resolved for 14 days is retired by the same sweep, so that query paints cold again.
- **`database.store` defaults to `'memory'`.** `'indexeddb'` keeps one IndexedDB database per user bucket (`sp00ky-<bucket>`) and needs `@surrealdb/wasm` >= 3.1.0: the 3.0.x engine opened the store but failed every write (`An IndexedDB error occured: idb error`), so each session fell back to memory. 3.1.0 ships the engine as `@surrealdb/wasm-native`; a Vite app lists it in `optimizeDeps.exclude` next to `@surrealdb/wasm`. A store that still cannot open after a drop runs the session in memory (error log `falling back to in-memory`). Under `localEngine: 'sqlite'` or `'rows'`, `'indexeddb'` means OPFS.
- **`localEngine: 'rows'` is the client's own row store (experimental).** `services/database/rows-store.ts` (one append-only file per bucket on OPFS sync access handles: hashed batches, a flat typed-array index per table, checkpoints, compaction; opening replays only the writes since the last checkpoint), `rows-exec.ts` (the verbs; bodies are the JSON text the SQLite engine stores and cross the worker as transferred bytes, parsed once on the page), `rows-worker.ts`, `rows-cache-engine.ts` (extends `SqliteCacheEngine` for the op queue, epoch fencing and shared-tabs roles, replaces everything that renders SQL). Same answers as `'sqlite'`, checked against real SQLite in `rows-exec.integration.test.ts`; where SQL leaves an order open (ties on `orderBy`, children of an unordered `.related()`) it returns id order. Writes to `ROWS_DURABLE_TABLES` (outbox, pending writes, failed mutations, local CRDT edits) are flushed before they resolve, everything else within ~100 ms. Works with `sharedTabs`. A change to how the SQLite engine filters, orders or merges needs the same change in `rows-exec.ts`. Secondary indexes are hidden tables in the same store (ids `value\0rowId`, empty bodies, written in the row's own batch): one per field that holds record links (found as rows are written), one per field a query filters on with `=` (built on first use; a field with fewer than 8 distinct values is left to scans); the registry is a row of the hidden meta table. `prewarmRows()` / `ROWS_PREWARM_SNIPPET` start the worker and open the last bucket from the page head, before the bundle; the engine adopts that worker (`createTransport`), takes the answer the worker already gave to that `open` when there is one (so its first read is one trip, not two) and replaces the worker when the answer names another `ROWS_PROTOCOL`. The worker's `warm` reads one table's index per turn and only after 15 ms without an op (`warmStep`): read all at once, it made the page's first read wait 10 ms. Bump `ROWS_PROTOCOL` when the worker's messages change. Read ahead (`rows-prewarm.ts`, a file without imports so a build script can load the snippet from it): the engine saves a session's first reads (`select` / `by-ids` / `relation` within 3 s of connecting, JSON-safe payloads only, at most 24) in the prewarm record; the next load's prewarm sends them under ids `<= ROWS_AHEAD_ID` (the worker refuses anything but those reads there), and `createTransport` answers a matching read from the reply already in the page (`ReadAhead`), so the client's first reads cost no trip. Answers are dropped on the first op that is not a read, on an open of another bucket or under a role lock, and 3 s after adoption; never recorded with `sharedTabs`. `PaintCache` (`database.paintCache`, solo mode) keeps the reads of a session's first 3 s in localStorage; `engine.peekSelect` / `peekByIds` (optional on `LocalStore`) return that copy synchronously before the store is open, a write to any table it read drops it, the next read of the same request takes it again. A peek is for painting, the read that follows is the answer. The client uses it for a query's first render: `materialize` names its read by the query's view key (`fx.local.select(plan, params, paintKey)`, so the copy kept is the query's latest render whatever its id set was), and `registerLocal` seeds a new entry's `records` from `fx.local.peekSelect` with the same render set and the same cold filter (`renderRead` in `query/materialize.ts`), leaving it unnotified and unanswered; `materialize` then confirms or replaces the rows. Before `init()`: `Sp00kyClient.peekQuery(finalQuery)` hands those rows back synchronously on a client that is not open (the bindings' `eager` providers render with them). For that the paint key is `paintKeyOf(def, ids)` in `query/materialize.ts`, the query's text and parameters (no digest: a component asks while it renders), with a `\ncold` suffix for a cold scan so a closed client, which cannot apply the cold filter, only ever gets a membership render's rows; and the constructor tells the engine which bucket boot will open (`expectBucket(readBootBucketHint() ?? 'anon')`, solo mode only). Calls made before `init()` finished wait for it instead of failing (`opened()`: `query().run()`, `queryRaw`, `preload`, `create` / `update` / `delete`, channel writes, `openCrdtField`, every `BucketHandle` method; the feature flag and app release registrations wait while there is no session yet), and reject with its error if it fails; `whenReady()` is the same promise for apps. `followerReads: 'direct'` (with `sharedTabs`): the leader's worker opens the files with `readwrite-unsafe` handles (`share` in the `open` payload), and a follower starts a worker of its own on a `RowStore` in reader mode (`RowStore.open(io, { reader: true })`: never writes, `refresh()` replays what was appended, `current()` after a read says whether a compaction moved the file under it; `handleReaderOp` retries then) and routes `ROWS_READER_OPS` to it (`rawCall` override), everything else to the leader's port; any failure of the reader falls back to the port. A reader builds no index (`RowsExec` `readOnly`) and re-reads the registry when the leader rewrites it. `dist/rows-worker.js` is built on its own (third tsdown config) so it is one self-contained file starting with the V8 compile hint `//# allFunctionsCalledOnLoad`. Benchmark: `apps/storage-bench`.
- **`database.workers` lets the app start the local store's worker.** Only for a bundler that does not bundle a `new Worker(new URL(...))` inside a dependency, i.e. the Angular CLI: `workers.surreal` returns a module worker whose entry is `import '@surrealdb/wasm/worker'`, `workers.sqlite` (with `localEngine: 'sqlite'`) one whose entry is `import '@spooky-sync/core/sqlite-worker'`, `workers.rows` (with `localEngine: 'rows'`) one whose entry is `import '@spooky-sync/core/rows-worker'` (exports kept in `sideEffects` so the bare import survives tree shaking). Unset, the built-in worker expressions run as before; Vite / Rollup / webpack apps leave it unset.
- **Boot owns the first identity.** The facade subscribes to auth with `immediate: false`: boot opens the bucket the hint names and `auth.restoreSession` announces the user. `LocalDatabaseService.switchStore` also waits for an in-flight `connect`, and lets statements already past the gate finish before it closes a client: the 3.1 engine streams results from its worker, and a statement whose client closed under it stayed pending until its 30 s deadline with every later local statement queued behind it.
- **A rejected write is not lost.** Application errors roll the local row back (create/update/delete) and move the mutation to `_00_failed_mutations`; the tray API above lists, retries (as a fresh write) or discards it. Network errors keep the row queued, and so does a write SurrealDB refused only because sp00ky's own `_00_` ingest event could not post to the scheduler/SSP (refused, past its TIMEOUT, DNS, 5xx/408/429; `SP00KY_EVENT_POST_FAILED` in `utils/error-classification.ts`).

## Module map (under `src/`)

- `kernel/` — `Effect` union, saga driver + lanes, constants, interpreter.
- `state/` — `ClientState`, lifecycle machine, reducers (they mark queries dirty), selectors (`overlay`, `needed`, `planFetch`, `settled`, `evictable`, `phaseTimings`).
- `query/` — keys, membership rules, render set, SQL, and the sagas: `register`, `membership`, `fetch`, `materialize`, `lifecycle`.
- `mutation/` — outbox rows (v2: `tableName`, `beforeRecord`, `createdAt`), `write`, `push` (drain + rollback), `tray`, jobs.
- `sync/` — `poll`, `live`, `connection` (health, self-heal), `tabs` relay, pure policy.
- `boot/` — `boot`, `auth-flip`, `bucket-switch`, `preload`.
- `client/` — `runtime`, `router` (event -> saga + lane), `services` (adapters), `sp00ky-client` (facade), `bucket-handle`.
- `testing/` — `runPure` (drive a saga with canned effect results), fake adapters/services, state builders.
- `modules/` — auth, crdt, feature-flag, app-release, devtools, ref-tables (unchanged adapters).
- `services/` — local store engines, remote socket + supervisor, SSP wasm wrapper, tabs broker, blobs, persistence, logger.

Rules: nothing under `kernel/state/query/mutation/sync/boot` imports `services/` or touches `Date`, `setTimeout`, `crypto`; those directories are gated at 100% coverage. Legacy services are reached through the typed `service` effect (`kernel/effects.ts`, `ServiceCalls`).
