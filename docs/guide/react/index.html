React guide

Use Sp00ky from a React app: Sp00kyProvider, useQuery with structural sharing, useSubmission, status hooks and bucket images.

@spooky-sync/client-react is the React binding. It wraps the same core client as the Solid bindings and exposes the same hooks, written the React way: they return plain values instead of accessors, and they re-render only when what they return changed. It works with React 18 and 19.

React DOM, not React Native

The core client runs SurrealDB and SQLite as WebAssembly in the browser, with IndexedDB / OPFS storage and web workers. React Native’s runtime has none of these, so this package targets React in the browser (Vite, Next.js client components, Remix, and so on). For a native mobile app use the Flutter guide.

What “native” means here

  • Tear-free reads. Every hook reads its state through useSyncExternalStore, so a concurrent render never sees two different versions of a query or of the sync status.
  • Structural sharing. Each live emission is merged into the previous result: rows are matched by id, unchanged rows keep their object identity, and a deep-equal emission does not re-render at all. React.memo rows and useMemo deps keyed on a row only re-run when that row changed.
  • Lifecycle in effects. The client, query registrations, CRDT fields, channels and file leases are opened in effects and released in their cleanups, never during render. StrictMode’s double mount ends with exactly one of each.
  • No optimistic layer. The engine already commits writes locally and re-renders through live queries before it syncs. Mutations are plain await db.create(...) calls; useSubmission only adds button pending and error state.
  1. Install
    pnpm add @spooky-sync/core @spooky-sync/client-react
pnpm add -D vite-plugin-wasm vite-plugin-top-level-await
  2. Configure the bundler

    The core client loads its engines as WebAssembly. With Vite, keep them out of dependency pre-bundling and allow top-level await:

    vite.config.ts 
    import { defineConfig } from 'vite';
import react from '@vitejs/plugin-react';
import wasm from 'vite-plugin-wasm';
import topLevelAwait from 'vite-plugin-top-level-await';

export default defineConfig({
  plugins: [react(), wasm(), topLevelAwait()],
  optimizeDeps: {
    exclude: ['@surrealdb/wasm', '@surrealdb/wasm-native', '@sqlite.org/sqlite-wasm'],
  },
  build: { target: 'esnext' },
});

    See Client config for why each package is excluded.

  3. Generate types
    spky generate

    Same generator as every other client, see Generated types.

  4. Configure the client
    src/db.ts 
    import type { SyncedDbConfig } from '@spooky-sync/client-react';
import { schema, SURQL_SCHEMA } from './schema.gen';

export const dbConfig: SyncedDbConfig<typeof schema> = {
  logLevel: 'info',
  schema,
  schemaSurql: SURQL_SCHEMA,
  database: {
    namespace: 'main',
    database: 'main',
    // spky dev exposes SurrealDB on 8666 by default.
    endpoint: 'ws://localhost:8666/rpc',
    store: 'indexeddb',
  },
};

    Every key is documented in Client config.

  5. Mount the provider
    src/App.tsx 
    import { Sp00kyProvider } from '@spooky-sync/client-react';
import { dbConfig } from './db';
import { MainContent } from './MainContent';

export default function App() {
  return (
    <Sp00kyProvider
      config={dbConfig}
      fallback={<div>Initializing database…</div>}
      preload={async (db) => {
        // Optional: warm the local cache before the UI is revealed.
        await db.preload(db.query('config').build());
      }}
      onError={(err) => console.error('Failed to initialize database:', err)}
    >
      <MainContent />
    </Sp00kyProvider>
  );
}

    Props match the Solid providers: config, fallback, preload (awaited before the children render), onReady, onError. The client is created in an effect, so a server render only produces the fallback. config is read once when the provider mounts; to switch databases, remount it with a new key. A client that was handed to the tree is deliberately not closed on unmount.

Queries

useQuery(query, options?) takes a built query. Build it inline: the hook re-registers only when the query’s identity (its SurrealQL and vars) changes, not when a new query object is created on every render.

src/components/PostList.tsx 
import { useDb, useQuery } from '@spooky-sync/client-react';
import type { schema } from '../schema.gen';

export function PostList() {
  const db = useDb<typeof schema>();
  const posts = useQuery(
    db.query('post').related('author').orderBy('created_at', 'desc').limit(20).build()
  );

  if (posts.isLoading) return <div>Loading…</div>;
  if (posts.isEmpty) return <div>No posts yet.</div>;
  return (
    <ul>
      {posts.data.map((post) => (
        <li key={String(post.id)}>
          {post.title} by {post.author?.username}
        </li>
      ))}
    </ul>
  );
}

Pass null (or { enabled: false }) to skip a query until its inputs exist:

const post = useQuery(
  postId ? db.query('post').where({ id: postId }).one().build() : null
);

useQuery(db, query, options?) takes the client explicitly, for code outside a provider.

Result surface

The flags are the same contract as the Solid 2 binding, as plain values:

FieldMeaning
dataRows, or the row / null for .one(). [] / null before the first result. Structurally shared between emissions.
errorRegistration or sync error (e.g. SSP 503 during bootstrap). Never thrown; the sync scheduler retries underneath.
isLoadingCold first load only: nothing painted for this identity, the server has not answered, and registration has not failed. A paint from the local cache ends it; the server answering with zero rows ends it too.
isFetchingThe sync engine is pulling records for this query (registration, a sync round).
isAuthoritativedata holds the rendered rows of a known membership: the server’s answer, or the one a previous session left on this device. From here data is an answer, not a cache guess.
hasDatadata holds something: rows for a list, a row for .one().
isEmptyAuthoritative and no data: the server said “no rows”. Render empty states on this, never on a bare !hasData.
isSettledAuthoritative and idle. The gate for trusting a short window as the end of a list, and for “create it if it is missing”. Not monotonic: a later sync round re-enters isFetching.

When the query’s identity changes, the previous data stays on screen until the new identity emits, while the flags reset. Growing a .limit() therefore never flashes an empty list:

const [limit, setLimit] = useState(20);
const posts = useQuery(db.query('post').orderBy('created_at', 'desc').limit(limit).build());

<button disabled={!posts.isSettled} onClick={() => setLimit((n) => n + 20)}>
  Load more
</button>

Options: { enabled?: boolean, deregisterOnCleanup?: boolean }. Use deregisterOnCleanup for viewport windows that mount and unmount a query per page, see Pagination.

Memoized rows

Because unchanged rows keep their identity, a memoized row component skips the render when another row changes:

const PostRow = memo(function PostRow({ post }: { post: Post }) {
  return <li>{post.title}</li>;
});

{posts.data.map((post) => <PostRow key={String(post.id)} post={post} />)}

Preloading

usePreload(query) warms the local cache for a query the user is likely to open next, without subscribing to it:

import { usePreload } from '@spooky-sync/client-react';

function ThreadLink({ id }: { id: string }) {
  const db = useDb<typeof schema>();
  usePreload(db.query('thread').where({ id }).related('comments').one().build());
  return <Link to={'/thread/' + id}>Open</Link>;
}

Mutations

Engine writes are already optimistic and local-first, so mutations are plain calls:

await db.create('post:' + crypto.randomUUID(), { title: 'Hi' });
await db.update('post', 'post:xyz', { title: 'Edited' });
await db.delete('post', row.id);
await db.run('backend', 'sendMail', { to });

For button pending and error state, wrap the call in useSubmission. submit is stable across renders, always calls the latest function, and never rejects:

import { useSubmission } from '@spooky-sync/client-react';

function NewPost() {
  const db = useDb<typeof schema>();
  const [title, setTitle] = useState('');
  const save = useSubmission((t: string) => db.create('post:' + crypto.randomUUID(), { title: t }));

  return (
    <form onSubmit={(e) => { e.preventDefault(); void save.submit(title); }}>
      <input value={title} onChange={(e) => setTitle(e.target.value)} />
      <button disabled={save.pending}>Save</button>
      {save.error && <p>{save.error.message}</p>}
    </form>
  );
}

An error there means the local commit failed. Sync failures surface through useSyncStatus and usePendingMutations instead. To track a backend job, query its outbox row: db.run() writes one with status: 'pending'.

Status hooks

Same shapes as the Solid bindings, returning values: useDb, usePendingMutations, useSyncStatus, useSyncActivity, useStorageStatus, useFeatureFlag, useAppRelease, useImpersonation and useCrdtField.

import { useSyncStatus, usePendingMutations } from '@spooky-sync/client-react';

function ConnectionBanner() {
  const sync = useSyncStatus();
  const pending = usePendingMutations();
  if (!sync.isDegraded) return null;
  return <Banner>Can't reach the server, {pending} change(s) queued.</Banner>;
}

Files and images

useFileUpload, useDownloadFile, useBlurhash, useBucketImage and the <BucketImage> / <Blurhash> components behave as in the Solid bindings. Paths are plain values, and the components take className / style / imgClassName.

import { BucketImage, useFileUpload } from '@spooky-sync/client-react';

function Avatar({ path }: { path: string | null }) {
  return <BucketImage bucket="avatars" path={path} className="h-12 w-12 rounded-full" alt="" />;
}

function AvatarUpload() {
  const { upload, isUploading, error } = useFileUpload('avatars');
  return (
    <input
      type="file"
      disabled={isUploading}
      onChange={(e) => {
        const file = e.target.files?.[0];
        if (file) void upload(crypto.randomUUID() + '.png', file);
      }}
    />
  );
}

Peer to peer channels

useChannel(query, peers) opens a channel while the component is mounted. Query and peers are compared by value, so building them inline is fine; null closes the channel.

import { useChannel } from '@spooky-sync/client-react';

const ch = useChannel(db.query('message').where({ conversation: convoId }), [me, other]);
// ch.status: 'idle' | 'connecting' | 'connected' | 'failed' | 'unsupported'
await ch.update('message', id, { draft: text });

Next.js

The bundle starts with 'use client', so a server component (an App Router layout) can render <Sp00kyProvider> directly. The provider renders its fallback on the server; data loads in the browser, from the local cache first.
